# 01 · 产品调研：用户、痛点、竞品与定位

> 上游基线：`00-task-brief.md`（唯一事实来源）。本文只覆盖**用户与产品定位**，不涉及技术选型、不涉及界面规格。
> 证据分级贯穿全文（见 §9）：`[F]` 公开事实 · `[I]` 合理推断 · `[V]` 待验证。
> **本文不含任何未经核实的百分比、用户量、榜单排名、市场规模数字。** 所有阈值均为「设计目标」，非实测结论。

---

## 0. 一句话结论

现有工具回答的是 **"这根管子有多粗"**；用户真正要回答的是 **"这根管子现在能不能把我要的活干完，干不完是哪一段坏了"**。

ProxyLens 要占的位置是 **「代理链路的业务可用性体检报告」**——体温计我们不缺，缺的是体检报告。

---

## 1. 目标用户画像

四类画像。**A/B/C 为首版主战场，D 为共存但不设专门功能的次战场。**

### A. 「AI 是生产工具」的重度用户（主战场 · 第一优先级）

| 维度 | 描述 |
|---|---|
| 典型身份 | 独立开发者、算法/研究员、AI 产品经理、自动化脚本作者 |
| 技术水位 | **高**。理解代理/节点/TUN/规则，看得懂日志，会用 `curl -w`、`mtr` 自证 |
| 使用频率 | 代理常年常开，每天多次感知「变慢/断流/被挑战」 |
| 主要业务面 | ChatGPT/Claude 网页 + API、Gemini、IDE 内推理、HuggingFace、arXiv、GitHub |
| 典型场景 | ① 早会前确认今天能不能开工 ② 长任务前确认链路撑得住 ③ 换节点后确认真的切换了 ④ 调 API 超时，要区分「我的代码」还是「链路」 |
| 打开那一秒的诉求 | **"别给我 200Mbps，告诉我能不能干活，坏在哪一层。"** 希望 3 秒内看到「可用/不可用 + 责任层」，数字是用来举证的 |
| 会被什么激怒 | 结论含糊（"网络一般"）、只给数字不给判断、把「能连」当「能用」 |
| 深层动机 | **避免误判成本**：误判为链路问题白折腾两小时，误判为代码问题同样白折腾两小时 |

### B. 「跨境协作」的工作型用户（主战场）

| 维度 | 描述 |
|---|---|
| 典型身份 | 远程雇员、跨境电商运营、海外 BD、留学与科研人员、内容创作者 |
| 技术水位 | **中**。会选节点、会开关代理，但不懂 TLS/SNI/DNS 污染，遇问题只能"换一个试试" |
| 主要业务面 | Google Workspace、YouTube（看 + 传）、Gmail、Slack/Notion、Figma、素材上传下载 |
| 典型场景 | ① 会前 5 分钟测 Meet 会不会卡 ② 传 2GB 素材前测上行 ③ 追剧前确认会不会转圈 ④ 客户投诉"你发的链接打不开" |
| 打开那一秒的诉求 | **"接下来这一小时，我能顺畅开会/传文件/看视频吗？"** 关注的是**未来一小段时间**的可用性，不是当下峰值 |
| 会被什么激怒 | 测出来"很好"、一开视频就缓冲；测出来很好、上传卡在 30% |
| 深层动机 | **保住体面**：会议卡住、上传失败，代价是社交与商业信用 |

### C. 「别人帮我配的」轻度用户（主战场 · 决定口碑与传播）

| 维度 | 描述 |
|---|---|
| 典型身份 | 朋友代配代理的普通用户、被机场广告吸引的入门用户、临时需要跨境访问的人 |
| 技术水位 | **低**。分不清 socks5 与 http 代理的区别，看到"节点/订阅/规则"就懵，不认识 TTFB |
| 主要业务面 | ChatGPT 网页、YouTube、Google 搜索、Instagram/X |
| 典型场景 | ① 打不开 ChatGPT，怀疑账号被封 ② 付了钱觉得不值但说不清哪不行 ③ 想找客服，只会说"用不了" |
| 打开那一秒的诉求 | **"到底行不行？要找人，我该把什么发给对方？"** 需要**一句人话** + **一份能直接转发的证据** |
| 会被什么激怒 | 满屏术语、看不懂图表、让他自己判断、绕一圈还是不知道要不要换 |
| 深层动机 | **降低无助感**：他真正想要的是一个「裁决」和一个「能甩给卖家的截图」 |

> ⚠️ 设计红线：面向 C 类，**任何 P0 结论都必须能用一句不含缩写的中文说清**。术语只能存在于第二层（展开/详情）。

### D. 技术支持 / 机场客服（次战场 · 只服务「出报告」）

| 维度 | 描述 |
|---|---|
| 典型身份 | 机场售后、公司 IT、帮朋友排查的人（多为 A 类兼任） |
| 需求 | 可复现、可对比、可转发的证据；能对照「开代理 vs 直连」；能标注时间与代理配置 |
| 打开那一秒的诉求 | **"给我一份能证明问题在他那边（或在我这边）的报告。"** |
| 明确边界 | **不做**账号体系、**不做**多节点批量压测、**不做**工单系统。只做「单次/单链路 + 导出」 |

### 1.1 画像共性：三句话

1. **没人想测速，所有人都想得到裁决。** 数字是论据，不是结论。
2. **所有人都在做同一件事：归因。** 是我的问题、节点的问题、还是对方的问题？
3. **所有人都不信任瞬时快照。** 因为所有人都被"测着很好、用着很烂"骗过。

## 2. 痛点分析：为什么「延迟测试 / 能连即通」不够用

### 2.1 根因：工具测的层，和用户出问题的层，根本不是一个层

| 协议层 | 现有工具的覆盖 | 用户实际出问题的地方 |
|---|---|---|
| L3/L4 连通性（TCP 握手、RTT） | **覆盖充分**（ping / URL Test / Speedtest） | 很少真正坏在这一层 |
| L5 TLS（握手、证书链、SNI） | 基本不测 | **高频故障层** |
| L7 HTTP 语义（状态码、挑战页、地区页、截断） | 几乎不测 | **最高频故障层**，也是"AI 不可用"的真实所在 |
| 应用层行为（分片下载、SSE 流式、range 请求） | 不测 | **"能开但用不了"的真实所在** |

**一句话：故障已经从「连不上」迁移到「连上了但用不了」，而工具还停在「连没连上」。**

### 2.2 八类真实痛点 → 机理 → 现有工具如何误判 → 我们必须测出什么

| # | 用户原话 | 现有工具的结论 | 真实机理 | ProxyLens 必须给出的证据 |
|---|---|---|---|---|
| **T1** | "节点 30ms 绿油油，网页就是打不开" | 「延迟极低，节点优秀」 | **假连接**：TCP 握手完成（可能由本地或中间设备代答），随后 TLS `ClientHello` 或首个 GET 被 RST 重置。握手成功 ≠ 数据可通 | 四段分层计时（DNS/TCP/TLS/TTFB），并把 **TCP 成功但 TLS 失败** 建模为「假连接」故障类型，而非笼统"失败" |
| **T2** | "浏览器报证书错误 / 提示不安全" | 「可达」 | **TLS 中间人劫持**：SNI 阻断、证书被替换（自签/企业防火墙 CA）、证书链不完整、TLS 版本被降级 | 记录 TLS 版本、证书 issuer/subject 摘要、链校验结果、握手耗时；区分「证书不受信」与「连接被重置」 |
| **T3** | "显示'请稍候…验证您是人类'" | 状态码 200 → 「完全正常」 | **Cloudflare/Akamai 人机验证**：200 返回的是 challenge 页（`cf-mitigated`、`cf-chl`、`/cdn-cgi/challenge-platform`、`Just a moment...` 标题等特征） | **不能只看状态码**：响应头 + 响应体 + 标题指纹三重识别，单独输出「被挑战」。被挑战既不是"通"也不是"不通" |
| **T4** | "ChatGPT 说我在不支持的国家/地区" | 200/403 → 「能打开」/「被墙了」 | **服务侧地区与风险策略**：出口 IP 被判定为不支持地区或高风险（机房 IP、被滥用 IP），返回 403/451 或专门的不支持地区文案 | 状态码语义 + 页面文案指纹 + 轻量出口地区推断；输出「地区/风控受限」，与「网络不通」严格分离 |
| **T5** | "白天好好的，一到晚上就废" | 测一次 → 「很快」 | **时间维度上的能力衰减**：晚高峰争抢、节点超售、跨境拥塞。单次快照无法表达 | p50/p90 + 变异系数（CV）+ 吞吐衰减曲线（前 3s 与后 20s 速率比）；并提供**带时间戳的历史记录**让"晚上变差"可见 |
| **T6** | "YouTube 首页能开，点开视频一直转圈" | 「YouTube 可达」 | **页面域与媒体域分离**：`youtube.com` 通，但承载视频的 `*.googlevideo.com` 被限速/阻断；或 QUIC/UDP 被拦后回退缓慢 | **分域测量**：分别测 `youtube.com` 页面链路 与 `googlevideo.com` 分片（range 请求），输出起播耗时 + 分片速率 |
| **T7** | "ChatGPT 能开能登录，发消息一直转圈" | 「ChatGPT 可用」 | **读写走不同路径**：静态页来自 `cdn.oaistatic.com`（CDN，容易通），对话请求走 POST + SSE 流式响应，易被风控/限速/中断 | 区分「页面可达」与「推理链路可用」；把流式首包延迟与是否中断作为独立观测（首版可轻量替代，见 §6 边界） |
| **T8** | "大文件下到 30% 断了 / 速度一路往下掉" | 「平均速度还行」 | **PMTU 黑洞 / 中途限速 / 单连接整形**：小请求正常，大包或长连接被丢 | 固定字节量**流式下载** + 速率采样序列，输出衰减曲线与中断点，而不是只报一个平均 Mbps |

### 2.3 三类"隐性误判"，必须单独强调

| 误判 | 说明 | 后果 |
|---|---|---|
| **把「能连」当「能用」** | TCP/TLS/200 全过，业务层不可用（T3/T6/T7） | 用户以为没问题，开工即翻车。**这是本产品存在的第一理由** |
| **把「一次」当「一直」** | 单次快照 + 无时间戳，无法区分"稳定"与"此刻恰好" | 用户对工具整体失去信任，认为"测速都是玄学" |
| **把「不通」当「墙」** | 403/451/挑战页/超时全归为"被墙" | 用户做出错误处置：换节点（无效）、换机场（无效）、找客服吵架（无效） |

### 2.4 用户当前的"土办法"（证明需求真实存在）

- 开浏览器点开 ChatGPT，打几个字看回不回 `[I]`（最主流，C 类几乎唯一手段）
- 打开 YouTube 点一个视频看转不转圈 `[I]`
- `curl -o /dev/null -w "%{time_total}"` 手搓计时（A 类常用）
- 在代理客户端里反复点「URL Test」，哪个数字小就切哪个 `[I]`
- 去第三方「ChatGPT 可用性检测」网页点一下，看到"可用"就放心（缺口见 §3）
- 问群 / 问客服，靠人工经验对齐 `[I]`

> **这些土办法的共同特征：它们测的都是「业务行为」，只是靠人眼和手工完成。** 产品要做的是把这些**已经在发生的人类行为仪器化**，而不是发明新指标。

## 3. 竞品分析

### 3.1 主表

| 品类 / 代表 | 测量对象 | 真实测了什么 | **明确不测什么** | 交互范式 | 可借鉴点 | 缺口（= 我们的机会） |
|---|---|---|---|---|---|---|
| **Cloudflare Speed Test**（speed.cloudflare.com）`[F]` | 链路吞吐 + 负载下延迟 | 下载/上传吞吐、空闲与**负载下**延迟、jitter、丢包（对 Cloudflare 边缘做真实 HTTP 传输） | 不测具体业务站点；不测 TLS 中间人；不测 AI 站点语义；不测地区限制 | 一键启动 → 数字逐项填充 → 分位数图表 | ①**「负载下延迟」**概念（远比空闲延迟真实）②**分位数呈现**而非单一均值 ③ 克制专业的可视化 | 与"我能不能用 ChatGPT"零关联；用户看到 300Mbps 仍不知道能不能开工 |
| **fast.com**（Netflix）`[F]` | 链路下行吞吐 | 下载吞吐（以视频流为负载） | 只测下行；不测延迟/稳定性/业务语义 | 打开即测、零输入、**一个巨大数字**、无配置项 | ①**"打开即测、零输入"**——降低 C 类门槛的极致范式 ②单一核心结论的视觉勇气 | 单指标到极致，但无归因能力；测完等于没测 |
| **Speedtest.net**（Ookla）`[F]` | 链路上下行 + ping | 下载/上传、ping、jitter、丢包，自动选最近测速服务器 | 不测业务站点；服务器选择对"代理路径"不友好（可能选到与代理出口无关的节点）；不测 TLS/挑战页 | 仪表盘动画 + 服务器选择 + 结果卡可分享 | ①**结果可分享/可截图**（C/D 类的转发需求）②"测前可选目标"的心智 | **最容易误导的工具**：测的是"到测速服务器"的能力，不是"到业务"的能力。是用户误判的主要来源之一 |
| **LibreSpeed**（自托管开源）`[F]` | 链路吞吐 | 下载/上传/ping/jitter，可自建后端，实时曲线 | 同上，不测业务语义 | 实时折线图 + 明细分项 + 可换测试点 | ①**实时流式曲线**（过程可见，不只结果可见）②**明细分项 + 可换目标**（对应我们的三模式对照）③ 自包含无外部依赖 | 面向"运营商/机房测带宽"，与代理用户场景语义断开 |
| **各类「ChatGPT / OpenAI 可用性检测」网页** `[F]` | 业务可达性（薄） | 常见做法：DNS 解析、服务端一次性 GET、或浏览器 `fetch` 看 200/403 | **大多不测吞吐、不测稳定性、不测分片、不测流式**；判定常只有「可用/不可用」二元；部分靠浏览器 `fetch`，受 CORS/混合内容干扰会产生**假阴性**；且大多**测的是检测站自己的服务器**，而非"你本机这条代理"的真实路径 | 单按钮 → 一个绿/红标签 | ①**"业务语义判定"这个方向已被验证有需求** ② 极低的认知门槛 | **薄**：一元判定 + 无证据 + 路径错位（测的是别人的网络）。用户看完仍然不知道"是我的问题还是它的问题" |
| **代理客户端内置「URL Test / 延迟测试」**（Clash/v2rayN/Shadowrocket 等）`[F]` | 单节点的 HTTP 可达性 | 通过该节点 GET 一个 `generate_204`，得到 ms | **不测吞吐、不测业务语义、不测假连接、不测挑战页、不测分片**；且**只在客户端管理的节点内**测 | 列表中每个节点旁一个数字 + 一键"全部测速" | ①**"节点旁一个数字"的极简心智**（我们借其"低认知负荷"，但不借其指标）②批量并发测的即时感 | **本产品最需要正面区隔的对象**：它测的是「节点」，我们要测的是「这套代理整体 + 真实业务」。它给的绿点正是 T1/T3 误判的源头 |
| **流媒体 / IP 属性查询类工具**（解锁检测、IP 风险分查询）`[F]` | 单一站点可达性 / IP 属性 | 对特定站点做一次请求判断是否解锁；或查出口 IP 的归属与风险标记 | 不测速度与稳定性；不承诺业务完整可用 | 列表打勾/打叉 | ①**"地区限制页"识别思路**可复用 ②「出口 IP 属性」与 AI 风控的关联值得纳入结论解释 | 与 brief §3 一致：我们**不做解开锁数据库判定**，只在结论里做「地区/风控受限」的轻量归因 |
| **手工方法：`curl -w` / `mtr` / 浏览器人眼验证** `[F]` | 真实业务 | 真实请求的真实耗时 | 无标准化、无可视化、无历史、无法对比 | 无 | ①**TTFB / 分段计时**的度量口径 ②「用真实业务请求做探针」这一根本思路 | 门槛高，只有 A 类用得起。**我们的机会正是把 A 类的手艺变成 C 类可用的产品** |

### 3.2 竞品结论（三条）

1. **测速类工具（Cloudflare/fast/Speedtest/LibreSpeed）全部停在链路层**，做的是"管子有多粗"，且已做得很好——我们**不该在这个维度竞争**，也不应重复实现它们已有的严谨度（如负载下延迟），只需借用其呈现范式。
2. **可用性检测类网页已经证明了"业务语义判定"有真实需求**，但普遍**薄、偏、无证据**（一元结论 / 测的是自己服务器 / 无速度无稳定性）。这是我们最直接的替代对象。
3. **代理客户端内置测速是"错误心智"的主要供给方**。产品必须在文案上主动**否定**它："延迟低 ≠ 能用"。这不是攻击竞品，是纠正行业默认认知。

### 3.3 与「节点测速器」的边界（防止团队自己走偏）

| 维度 | 节点测速器（我们**不是**） | ProxyLens（我们是） |
|---|---|---|
| 测量单位 | 单个节点 / 单个订阅 | **整套系统代理环境**（含不填代理走系统/TUN 的情形） |
| 目标对象 | `generate_204` 等中性地址 | **OpenAI / Gemini / YouTube / Google CDN 等真实业务目标** |
| 输出 | 延迟 ms、丢包率、排序 | **可用性判断 + 归因 + 分项指标 + 可导出证据** |
| 典型问题 | "哪个节点最快" | **"我这套环境现在能不能干活，坏在哪"** |
| 用户动作 | 切节点、换订阅 | **判断、报修、决定是否换服务商、向人举证** |

> ⚠️ 纪律：**任何"帮用户挑节点"的功能提案默认拒绝**，除非 brief 被修改。

### 3.4 我们不做的（与竞品正面错位，避免范围蔓延）

- 不做裸带宽基准测试（用户要装测速仪，会去 Cloudflare/Speedtest）
- 不做节点批量测速排行榜（brief §3 已排除）
- 不做流媒体解锁全库判定（只做地区限制**页特征**识别）
- 不做 IP 落地/风险分数据库（只做轻量出口地区推断，并在 UI 上明确标注"推断"）

## 4. 差异化定位

### 4.1 一句话定位

> **ProxyLens 用真实业务请求，测量「这套代理能不能把 AI 和跨境业务跑完」，并直接给出可分责、可执行的结论——而不是一堆需要用户自己解读的链路数字。**

三个不可让渡的关键词：

1. **真实业务**：探测单位是"ChatGPT 页面 / Gemini 页面 / OpenAI API / YouTube 分片 / Google 大文件"，不是 `generate_204`。
2. **可分责**：结论必须能回答"是我的网络、我的节点、还是对方服务"。
3. **可执行**：每个结论后面跟一个动作建议（换节点 / 换时段 / 找客服 / 无需处理）。

### 4.2 定位坐标图（两轴，文字版）

```
 输出形态
   可执行判断
       ▲
       │  Q3                                    Q4
       │  「链路红绿灯」                        ★ ProxyLens（空位）
       │  代理客户端 URL Test                   业务 × 判断
       │  （绿点/ms，二元，链路层）              真实业务探测 + 分责归因 + 动作建议
       │                                        + 时间维度与直连对照
       │
       │  Q1                                    Q2
       │  「链路仪表盘」（红海）                 「业务薄探针」
       │  Speedtest / fast.com /                各类 ChatGPT 可用性检测网页
       │  Cloudflare Speed Test / LibreSpeed    （一元可用/不可用，无证据无速度）
       │
       └──────────────────────────────────────────────────────────▶ 测量对象
         链路（管子多粗）                        业务（活能不能干完）
   原始数字
```

| 象限 | 谁在这里 | 我们为什么不去 / 为什么要去 |
|---|---|---|
| **Q1 链路 × 数字** | Speedtest、fast.com、Cloudflare、LibreSpeed | **红海，且已做得很好。不去。** 赢不了，也不该赢——这是别人的专业 |
| **Q3 链路 × 判断** | 代理客户端 URL Test（绿点） | **它看起来像"判断"，其实是"链路层的二元判断"**。这正是用户误判的源头。我们要在文案上明确否定它 |
| **Q2 业务 × 数字** | ChatGPT 可用性检测网页 | **薄探针**。方向对，但只到"数字/一元标签"就停了，且测错了路径（测的是检测站自己） |
| **Q4 业务 × 判断** | **空位** | **这就是我们要占的位置。** 无人做"业务层 + 可执行判断 + 分责 + 时间维度" |

### 4.3 第三维（真正的护城河，坐标图画不出来）

坐标图只有两轴，但差异化实际由**第三维：时间与对照**决定：

| 维度 | 竞品做法 | 我们的做法 | 用户价值 |
|---|---|---|---|
| **时间** | 单次快照 | 带时间戳的历史 + p50/p90 + 衰减曲线 | 回答"是今晚不行，还是一直不行" |
| **对照** | 无 | 「系统代理 / 手动代理 / 直连」三模式可对照 | 回答"是代理的问题还是本地网络的问题" |
| **语义** | 状态码 | 状态码语义化 + 挑战页/地区页/截断识别 | 回答"是墙、是风控、还是对方故障" |

> **护城河不是"我们能测更多东西"，而是"我们把『归因』这件事做成了产品能力"。**

### 5.1 JTBD 句式（Jobs To Be Done）

格式：**当我 ___，我想要 ___，以便 ___。**

| # | JTBD | 对应画像 | 对应痛点 |
|---|---|---|---|
| **J1** | 当我**准备开始一段需要 AI 的工作**时，我想要**在 30 秒内确认"现在这套代理能不能支撑我干活"**，以便**不必先打开三个网站试错再决定今天做什么** | A | T1/T3/T4 |
| **J2** | 当我**遇到"页面打开了但用不了"**时，我想要**知道卡在读路径、写路径还是风控**，以便**不再反复重启客户端、换节点而无效果** | A/C | T3/T7 |
| **J3** | 当我**准备开会 / 上传大文件**时，我想要**判断未来一小段时间的带宽与稳定性够不够**，以便**选择现在开始还是换个时间/换种方式** | B | T5/T8 |
| **J4** | 当我**付了钱但体验变差**时，我想要**一份能证明"确实变差了"的证据**，以便**向服务方主张，或做出换供应商的决定** | B/C/D | T5/全部 |
| **J5** | 当我**帮别人排查**时，我想要**一份带时间、带目标、带分层的报告**，以便**快速定位责任方而不是远程陪着试** | D | 全部 |
| **J6** | 当我**换了一个节点/机场**时，我想要**确认"真的变好了"而不是感觉变好了**，以便**不做无意义的反复切换** | A/B | T1（假连接）/T5 |

### 5.2 主旅程：从"怀疑"到"裁决"（五阶段）

| 阶段 | 用户心理 | 他在做什么 | 我们的设计责任 | 失败模式（必须避免） |
|---|---|---|---|---|
| **① 触发** | 烦躁、怀疑，可能刚被卡住 | 报错后、会前、上传失败后、付完钱觉得亏 | **零输入即可开跑**（不填代理 = 走系统代理） | 一进来就要求填代理地址/选协议 → C 类直接流失 |
| **② 首次判定（0–30s）** | 想要一个答案，不想看过程 | 盯着屏幕等"行不行" | **先给结论，后给证据**；过程可见但不打扰 | 只有进度条没有阶段性结论；跑完才出结果 |
| **③ 归因** | "那是谁的问题？" | 展开某一个红灯看细节 | 每个失败项必须标**责任层**（本地/代理/目标服务） | 只显示"失败/超时"，不给层 |
| **④ 处置** | "我该干什么？" | 换节点、换时段、找客服、或直接开工 | 每个结论后跟**一个具体动作**，而非泛泛建议 | "网络质量一般，建议优化网络"（废话） |
| **⑤ 举证/沉淀** | "我得留个证据" | 截图、导出、复制 | 一键复制人话摘要 + 导出 JSON/Markdown | 只能截图，无法导出结构化数据 |

### 5.3 30 秒内必须拿到的结论（首屏不可妥协的四件事）

用户在**首次打开、不填任何配置**的前提下，30 秒内（*目标*）必须看到：

| # | 必须看到的 | 形式要求 | 为什么不可妥协 |
|---|---|---|---|
| **V1** | **一个总分裁决** | 一句话中文，如「这套代理现在**可以**顺畅用 AI」/「**勉强**：能打开，但 ChatGPT 可能被风控」/「**不可用**」 | C 类用户只看得懂这个；A 类用户用它决定是否继续看细节 |
| **V2** | **AI 可用性三态**（ChatGPT / Gemini / OpenAI API） | 每项三态之一：**可用 / 受限（挑战/风控/地区）/ 不可用**。**禁止二元** | 二元判定会把 T3/T4 误报为"可用"，这是竞品最大的坑 |
| **V3** | **速度与稳定性的一眼判断** | 「够用 / 勉强 / 不够」+ 一个数字（如 p50 Mbps）。绑定业务语义：够不够开视频、够不够传文件 | B 类要的是"够不够"，不是"多少" |
| **V4** | **当前出网方式** | 明确显示「系统代理（未单独配置，走 TUN/环境）」/「手动代理 socks5://…」/「直连」 | brief §4 明确要求可识别并展示实际出网方式；这也是所有结论的前提，否则结论无意义 |

**明确禁止出现在首屏的内容**：TTFB、CV、p90、TLS 版本、证书 issuer、状态码数字。这些属于第二层（展开/详情/报告）。

### 5.4 关键交互原则（来自用户研究，供 07/08 使用）

| 原则 | 说明 | 依据 |
|---|---|---|
| **结论先行，证据后置** | 首屏只有 V1–V4；点开才见分层与曲线 | A 类要证据但不愿被淹没；C 类只要裁决 |
| **过程可见，结果不阻塞** | 边测边出分项结论（brief §2.5 流式刷新） | 30 秒等待中"有东西在动"降低焦虑 |
| **三态而非二元** | 可用 / 受限 / 不可用 | T3/T4 的误判根源就是二元 |
| **每条红灯配一个动作** | 换节点 / 换时段 / 找客服 / 无需处理 | J2/J4；"可执行"是定位三关键词之一 |
| **对照组可开** | 「直连」作为可选对照，不是必选 | brief §2.3；不加对照时结果依然成立 |
| **可导出、可复制** | 人话摘要（给 C/D）+ JSON/Markdown（给 D） | J4/J5 |
| **失败也必须产出结论** | 全失败时给"责任层 + 下一步"，而非错误弹窗 | 失败场景正是用户最需要工具的时刻 |

## 7. 成功指标（可量化，且可被验证）

> 全部为**设计目标值**，不是实测结果。验证方法见 §8。

### 7.1 北极星指标

| 指标 | 定义 | 目标 |
|---|---|---|
| **裁决有效率** | 用户在单次使用后，对"我现在能不能顺畅用 AI"形成了明确判断（而非"还是不知道"）的比例 | ≥ 85%（*目标*，用小样本可用性测试测量） |
| **结论与人工实测一致率** | ProxyLens 的三态结论与"人工按同一路径实际操作"的结论一致的比例 | ≥ 90%（*目标*，≥ 20 组人工标注样本，覆盖可用/受限/不可用三态） |

### 7.2 首次体验指标

| 指标 | 定义 | 目标 |
|---|---|---|
| **首屏结论时间** | 从点击开始到 V1（总分裁决）出现 | ≤ 30s（*目标*），轻量模式 ≤ 10s |
| **零输入完成率** | 不填写任何配置即可完成一次完整检测的比例 | 100% |
| **首次使用无需帮助率** | C 类用户在不看说明的情况下完成一次检测并正确复述结论 | ≥ 80%（*目标*） |
| **术语逃逸检查** | 首屏（V1–V4）不含 TTFB/CV/p90/TLS/状态码等术语 | 通过/不通过（硬性） |

### 7.3 归因质量指标（差异化核心）

| 指标 | 定义 | 目标 |
|---|---|---|
| **假连接识别率** | 构造"TCP 通但 TLS 被重置"的场景，工具能标为「假连接/TLS 失败」而非"成功" | 100%（*目标*，可用固定测试端构造） |
| **挑战页识别率** | 对返回 challenge 页（HTTP 200）的场景，工具能标为「受限/被挑战」而非「可用」 | 100%（*目标*） |
| **地区限制识别率** | 对返回地区不支持页的场景，能标为「地区受限」 | ≥ 90%（*目标*） |
| **误报率（把可用判为不可用）** | 在真实可用环境下判为不可用的比例 | ≤ 5%（*目标*）。**这是比漏报更致命的错误**：会直接摧毁信任 |

### 7.4 性能与工程指标（仅对齐可测口径，详见 brief §2.5）

空闲 CPU 近 0（*目标*：空闲 1 分钟内不掉电、风扇不转）｜单次轻量检测 < 10s（*目标*）｜检测全程 UI 无卡顿、指标流式刷新｜静态资源本地内嵌、**无外部 CDN 依赖**，离线时 UI 仍可打开并给出明确提示。

### 7.5 反向指标（用于发现产品变质）

| 反向指标 | 说明 | 红线 |
|---|---|---|
| **首屏数字密度** | 首屏出现的裸数字个数 | 超过 4 个即视为"退回体温计" |
| **二元判定残留** | 任一 AI 探测项只输出可用/不可用 | 0 容忍 |
| **"节点"一词出现** | 产品内出现"节点测速/节点排行"等表述 | 0 容忍（会摧毁定位） |

### 8.1 本文的证据来源（诚实交代）

## 10. 给下游的输入与约束

### 10.1 给 PRD（pm）

**必须继承（不可改写）**

1. 定位三关键词：**真实业务 / 可分责 / 可执行**。任一功能若不能落到这三点，优先级下调。
2. **三态而非二元**：ChatGPT、Gemini、API 三项的结论必须是「可用 / 受限 / 不可用」。这是与所有竞品的分界线。
3. **首屏四件事 V1–V4**（§5.3）为验收硬指标，包含术语逃逸检查。
4. **M2「展示实际出网方式」必须 P0 且首屏可见**（理由见 §6.5）。
5. 反向指标（§7.5）写入验收：首屏裸数字 ≤4、二元残留 0 容忍、"节点测速"表述 0 容忍。

**边界（不要写进去）**

- 不承诺 Netflix/Disney 解锁结论；地区判定只能标"推断"。
- 不做节点管理、订阅、批量测速、账号体系。
- 不测上传（首版），并需在文案中明示，避免预期落差。

**关于 PM 三点提问的直接回应**

- **人群**：P-A/P-B/P-C 三分法成立，与本文一致。但**建议增加第四类 P-D（技术支持/机场客服，次战场）**——它不是新功能来源，而是**"导出报告"这一能力的需求依据**；没有它，S5 会被质疑为过度设计。同时建议把 C 类（轻度用户）的优先级**提到与 A 类并列**，因为"一句话人话 + 可复制证据"是产品能否被传播的决定因素，也是最容易被工程视角牺牲掉的部分。
- **AI 语义判定是否已被竞品覆盖**：**没有**。现有"ChatGPT 可用性检测"网页只做到一元标签，且多数测的是**检测站自己的服务器**而非用户本机链路；测速类工具完全不做语义判定。**护城河判断成立。**
- **brief 未写、建议进 P0**：M2（实际出网方式展示）。建议进 P1：S3（直连对照）。详见 §6.5。

### 10.2 给探测引擎（engine）

1. **探测单位是业务请求，不是 `generate_204`。** `generate_204` 只能作为链路基线（S2），永远不能代表 AI 可用。
2. **必须采集的最小数据模型**（缺任一字段，叙事层无法完成归因）：
   `目标域名` / `出网方式` / `DNS 耗时` / `TCP 耗时` / `TLS 耗时与版本与证书链校验结果` / `TTFB` / `状态码` / `响应体指纹判定（挑战页/地区页/截断）` / `吞吐采样序列` / `时间戳`。
3. **状态码必须语义化，禁止直接透出数字**：200 / 401（可达）/ 403 / 429 / 451 / 5xx / 挑战页 / 地区页 / 截断，需各自对应一个稳定枚举。
4. **失败也要有结论**：超时、RST、TLS 失败必须能落到 T1/T2 的故障类型上，而不是统一报"失败"。
5. **分位数需要采样数下限**：未达下限时**不得展示 p90**（否则是伪精度）。建议在 06 中明确该下限。
6. **`socks5h`（远程 DNS）与 `socks5` 必须区分**，否则 DNS 污染场景无法归因。

### 10.3 给 UX / 交互（ux-arch）

1. **结论先行，证据后置**：首屏只放 V1–V4；四段计时、状态码、证书信息一律在第二层。
2. **过程可见但结论流式前置**：允许"AI 项先出结论、下载项后补速度"，不必等全部完成才给裁决（对齐 brief §2.5）。
3. **每条红灯必须配一个动作**（换节点/换时段/找客服/无需处理），否则违反"可执行"。
4. **三态需要独立的视觉语言**（不是"红/绿"两色）：「受限」既不是成功也不是失败，视觉上必须与二者都可区分——这是本产品最容易做错的一处视觉决策。
5. **失败态是一等公民**：全失败必须给"责任层 + 下一步"，不得弹错误框了事。
6. **不填代理是默认路径**，任何情况下不得把"填代理地址"设为前置步骤。
7. 关于分工：据团队名单，`07-ux-interaction.md` / `08-ui-spec.md` 属 **ux-arch / ui-designer** 的域。本文 §5.4 仅为**用户研究侧的输入**，不构成交互设计。

### 10.4 给架构 / 安全（arch, security）

1. **出口方式判定必须三源交叉**（系统代理设置 / 环境变量 / 直连探测），因为 brief §4 已出现三者不一致的实测情况。判定结果必须能解释"为什么我认为你走的是 TUN"。
2. **凭据不落盘**：手动代理的 `user:pass@` 只能在内存中存在；导出的报告中**不得包含凭据**（导出功能的安全约束）。
3. **探测行为本身不得触发风控**：对 OpenAI/Cloudflare 的高频重试可能让用户 IP 更快被挑战，需设置退避策略与并发上限（这也是 M10「可中断」的隐含理由）。
4. **响应体采样有边界**：识别挑战页/地区页只需头部字节 + 标题，不应完整下载页面，避免流量与隐私问题。
