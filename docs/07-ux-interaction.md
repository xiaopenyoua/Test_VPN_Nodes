### 0.2 与 PRD 的术语对账（重要：词表以 PRD §3.1 为准）

PRD v1.0 §3.1 已锁死**探测项 9 态**（`PASS / PASS_WITH_NOTE / SLOW / BLOCKED_BY_POLICY / CHALLENGED / RATE_LIMITED / TIMEOUT / NET_FAIL / SKIPPED`）；
任务书用的是另一套粗粒度词（`pending / running / ok / degraded / blocked / failed / skipped`）来描述**运行过程**。
二者不是同一根轴。本文拆成两条正交轴——这是前端最容易做错的一处：

| 轴 | 取值 | 归属 | 用途 |
| --- | --- | --- | --- |
| **Lifecycle**（生命周期） | `pending` → `running` → `settled`；提前出局为 `skipped` | 交互层 / 调度器 | 决定骨架、进度、能否展开、能否重测 |
| **Verdict**（结论） | **PRD §3.1 的 9 态，一个不多一个不少** | 引擎（`06`）+ PRD §3.1 | 决定徽章文案、三态族、结论类型（C1–C7）、下一步建议 |

映射（供 UI 与 `verdict.ts` 消费；**粗粒度词只用于内部沟通，不得出现在 UI 上**）：

| 任务书的粗粒度 | 落到 Verdict（PRD 9 态） |
| --- | --- |
| `ok` | `PASS` |
| `degraded` | `PASS_WITH_NOTE` / `SLOW` |
| `blocked` | `CHALLENGED` / `BLOCKED_BY_POLICY` / `RATE_LIMITED` |
| `failed` | `NET_FAIL` / `TIMEOUT` |
| `skipped` | `SKIPPED`（无结论，只有 `skipReason`） |

> **不新增枚举值。** 本文早期版本曾设想 `TLS_ERROR`、`UNSTABLE` 两个独立值，PRD 定稿后废除：证书错误归入 `NET_FAIL`（用 `subReason = tls_cert` 区分）；"不稳定"不是探测项状态，而是**结论层的 C6**（由 P6 采样推导）。详见 §3.2。

> **两个不可妥协的视觉互斥（PRD §3.1 强制规则 2 + 第 6 章 #7）**：
> ① `SLOW`（能但慢）与 `NET_FAIL`/`TIMEOUT`（不能用）**不得同色**；
> ② `CHALLENGED`（人机验证）与 `BLOCKED_BY_POLICY`（地区/451）**不得合并为"被墙"**——二者处置方式完全不同。
> 详见 §6.6 的三态族与受限子变体。

### 0.2.1 结论类型以 PRD §7.2 为准（C1–C7）

PRD §7.2 定义了 **7 类互斥结论 C1–C7 + 直连特例**，且**按顺序优先匹配、命中即停**。本文 §6.3 的 T1–T7 只是"呈现结构的示例"，**判定语义与结论文案模板一律以 PRD §7.2 为准**。前端实现要点：

- `verdict.ts` 输出的键应为 `C1…C7 / C_DIRECT_FAIL / C_DIRECT_PASS`，不是 T1–T7；
- 建议条数 **≤3**，按 PRD §7.5 优先级截断：环境修复 > 归因澄清 > 对照实验 > 配置调整 > 等待重试；**泛化建议（"建议优化网络"）一律砍掉**；
- **C3「能连，但用不了 AI」必须获得全场最强视觉重量**，且必须出现归因句「本次问题不在速率」——这是产品唯一护城河。


### 0.3 一条贯穿全文的原则

界面在任何时刻都要让用户能回答三件事，且分别对应三套完全不同的动作：

1. **出去了吗？**（出网层）→ 检查代理开关 / 端口 / TUN
2. **出去后快不快、稳不稳？**（链路质量层）→ 换节点 / 换时段 / 降预期
3. **平台放不放行？**（平台风控层）→ 换落地地区 / 换 IP / 稍后重试

### 1.2 排序依据与缺席降级

| 区块 | 回答什么问题 | 何时存在 | 缺席时 |
| --- | --- | --- | --- |
| A Header | 我现在走哪种出网？ | 恒在 | — |
| B Config | 要测什么、花多少流量？ | 恒在；`running` 折叠为一行只读摘要（模式 + 地址 + 档位 + 预算），点摘要展开 | — |
| C Verdict | **所以能不能用？** | `running` 有首个终态即出现草稿版；`done`/`partial` 出终版 | `idle`/`configuring` 时替换为引导块「选好出口方式，按 ⏎ 开始」 |
| D ScoreStrip | 好在哪、差在哪？ | ≥1 项 settled | 骨架占位，不显示 0 分 |
| E ProbeGrid | 证据在哪？ | 恒在；`idle` 时 6 张空态卡兼任"将要测什么"的预告 | — |
| F Compare | 是代理的锅还是本来就慢？ | 对照开关开启且两轮都有结果 | **不占位**，不出现空壳 |
| G Detail | 为什么是这个结论？ | 用户展开某卡 | — |
| H Footer | 这次结果可不可信？ | 恒在 | — |

### 1.3 三个关键决策

**决策 1：C 在 E 之上，且 `running` 阶段就以草稿形态增量生长。**
产品承诺是"边测边给结论"。若结论只在最后出现，8–10 秒里用户面对 6 个跳动数字，体验退化为测速器。结论必须分级抬升：
`正在确认出网层…` → `出网正常，正在测带宽` → `带宽良好，正在确认 AI 平台放行` → 终版。

**决策 2：一张卡正面只允许一个主数字。**
判定规则：**哪个数字决定这张卡徽章的颜色，哪个就是主指标。**
P1 主位 Mbps（TTFB 降为次指标）；P3/P4/P5 主位是结论短语而非数字（数字在详情里）；P6 主位成功率。禁止正面塞表格。

**决策 3：轻量档被跳过的项，必须"显式未测"，不得用 0 分或通过色冒充（PRD US-04.3）。**
呈现为灰色虚线卡 + `本次未测` 徽章，且不参与总分权重（分母剔除，并在总分旁标注"N/6 项计入"）。

### 1.4 首屏契约（V1–V4 硬指标）

来自用户研究（`01-product-research.md` §7.2）：**30 秒内、不滚动、不展开**，用户必须完成判断。首屏并非"第一页"，而是 `running` 结束后的**首个可视区**。

| 槽位 | 必须出现 | 表达约束 |
| --- | --- | --- |
| **V1** 裁决 | 一句话总分结论 | 中文，**无缩写**。「可以顺畅用 AI」而非「AI 可用性 82 分」 |
| **V2** 三态 | ChatGPT / Gemini / OpenAI API 三项各自的三态 | 见 §6.6 三态视觉通道 |
| **V3** 速度 | 「够用 / 勉强 / 不够」+ 一个数字 | 数字必须绑定业务语义：「够开 1080p 视频」而非「p50 42.6 Mbps」 |
| **V4** 出网 | 当前出网方式（系统代理 / TUN 或全局接管 / 自定义 / 直连） | 枚举值，非自由文本 |

**首屏禁用词（验收项，出现即不通过）**：`TTFB`、`CV`、`p90`、`p50`、`TLS 版本`、证书 `issuer`、任何裸状态码数字（`403` / `401` / `451`）。

状态码只能出现在**详情层**（§8 证据区）。这是硬边界：状态码是本产品的证据，不是本产品的语言。

**布局含义**：V1–V4 必须挤进 `1440×900` 的**首屏**（不含滚动）。因此 B 区 Config 在 `done` 状态必须折叠为一行摘要，D 区 ScoreStrip 与 V1 合并呈现（总分 + 三态 + 速度语义句同处一屏），否则首屏必然溢出。这是 §11 响应式的**首要约束**，优先于任何栅格美观考虑。

**折叠行的内容规格（这是 V4 唯一的家，受保护约束）**

Config 折叠后的一行 `ConfigSummary` **必须原样保留出网方式摘要**，且该片段：

| 规则 | 要求 |
| --- | --- |
| 内容 | `模式 + 出网方式枚举值`，例：`系统代理 · TUN 或全局接管` / `自定义 · socks5h://127.0.0.1:7890` / `直连` |
| 不可折叠 | 出网方式是**不可折叠项**——折叠可以吃掉档位、预算、地址全文，不能吃掉它 |
| 权重 | 与 V1 同级：同一视区、非 hover 可见、不靠 tooltip、不缩为图标 |
| 为什么 | V4 是用户能否相信这份结论的**前提条件**。结论与出网方式必须同屏对照，否则"测的是 TUN 还是直连"无从判断，用户会怀疑整份报告（§7.1 常驻说明块同理） |
| 空间 | 与 `ConfigSummary` 的 40px 单行高度共用，不额外占行——ui-designer 已按 40px 核算，此处不再加高 |

> 该行是「首屏契约 V4」与「ConfigBar 折叠」两个约束的交点。任何"折叠后只剩一个『配置』按钮"的方案，等于把 V4 移出首屏，判为不通过。


### 1.5 全局状态词汇表（全站统一，禁止各组件自造）

| 概念 | 中文固定用语 | 禁止说法 |
| --- | --- | --- |
| 出网方式 | 系统代理（HTTP）/ 系统代理（SOCKS）/ TUN 或全局接管 / 环境变量代理 / 直连 / 无法识别 | "已连接 VPN"、"代理已开启" |
| 探测结论 | 正常 / 可用但有注记 / 被人机验证拦截 / 被地区策略拦截 / 被限流 / 未连通 / 超时 / 证书异常 / 不稳定 / 偏慢 | "失败"作为唯一兜底词 |

## 2. 页面流

### 2.1 主流程

```
S0 首次进入（idle）
  · 模式默认「系统代理」，地址框**可编辑但为空**（空是默认值，不是锁定态——
    不允许用 disabled 表达默认，否则手动代理路径被锁死，A 类用户与 M6/S4 场景直接出局）
  · 「留空 = 走系统默认出网路径」由三处提示承担认知纠偏：placeholder / 常驻说明块 / HeaderBar 实测徽章
  · 出网方式探测异步进行，HeaderBar 徽章先显示「识别中…」（≤1s 内落定，PRD US-01.2）
  · 档位默认「轻量」，展示流量预算「约 62 MB」
  · 「开始检测」可点（PRD US-01.1：零输入即可开跑）
  · C 区 = 引导块；E 区 = 6 张空态卡
        │ 用户触碰任一同配置项（切模式 / 输地址 / 换档位 / 开对照）
        ▼
S1 配置（configuring）
  · 地址框启用；逐字符校验；凭据即时打码
  · 「开始检测」保持可点（永不 disabled，见 §7.2），非法时点击 → 聚焦输入框 + 行内错误
        │ Enter 或点击「开始检测」
        ▼
S2 running · 冷启动 0–400ms
  · 6 卡 pending → running，出现阶段 stepper
  · C 区草稿：「正在确认出网层…」
  · B 区折叠为一行只读摘要；主按钮变「取消检测」（始终可见，PRD US-05.1）
  · 预算行切换为「已用 3.2 MB / 约 62 MB」
        │ 首个 probe 顶事件
        ▼
S2' running · 流式 400ms–10s（轻量档）
  · 每项达终态 → 该卡局部变徽章 + 定格主指标；该卡立刻可展开
  · C 区按已确定层级逐级抬升草稿
  · D 区分项分随项数增加而收敛，未足项的分数显示为「—」而非 0
  · 任一卡「重测」可用（同一时刻仅 1 个在飞）
        │ 全部 settled                    │ Esc / 取消
        ▼                                 ▼
S3 done                            S5 cancelled（瞬态，仅 1 帧）
  · 结果完整，C 终版                  · 未完成项标 skipped(reason=cancelled)
  · 可导出 / 可重测 / 可改配置         · 已 settled 结果保留
        │                                 │ 有 settled 项 → S4 partial
        │                                 │ 无 settled 项 → S0 idle
        │ 重测单项/全部 → S2'
        ▼
S4 partial
  · 存在 skipped 或未达终态项
  · C 区措辞降级：「基于 5/6 项检测的初步结论」，并列出缺哪项
  · 总分旁标注「5/6 项计入」；导出文件头写 incomplete
S6 failed（终止态）
  · 触发见 §3.3；ErrorBanner 置顶，C 区替换为根因说明 + 修复入口
  · 6 卡保留现场（全部 failed 或混合），不做清空
```

### 2.2 状态进入/退出条件

| 状态 | 进入条件 | 退出条件 | 结果是否保留 |
| --- | --- | --- | --- |
| `idle` | 启动；点「清空结果」；取消且无任何 settled 项 | 触碰配置 → `configuring`；开始 → `running` | 无 |
| `configuring` | `idle`/`done`/`partial`/`failed` 下修改模式、地址、档位、对照开关、高级项 | 开始 → `running`；撤销全部改动且原本无结果 → `idle` | 保留旧结果，但立刻弹**阻断式**「配置已修改」提示（附录 C-5），不是角落提示条 |
| `running` | 校验通过 + 用户触发；或任一项重测 | 全部 settled → `done`/`partial`；取消 → `cancelled`；系统级错误 → `failed` | 累积中 |
| `partial` | 结束时有 ≥1 项为 skipped 或未达终态 | 补齐重测 → `done`；重跑 → `running`；清空 → `idle` | 保留 |
| `done` | 6 项全部达到终态且无 skipped | 重测 → `running`；改配置 → `configuring` | 保留 |
| `cancelled` | `running` 下按 Esc 或点取消 | **瞬态**，1 帧内转 `partial`（有结果）或 `idle`（无结果） | 见左 |
| `failed` | 见 §3.3 | 重试 → `running`；改配置 → `configuring` | 保留现场 |

> **对任务书的一处修正**：`cancelled` 无法作为稳定 UI 状态存在——取消后用户必然看到"半份报告"或"回到初始"。本文将其定义为瞬态过渡态，唯一职责是裁决"已 settled 的结果是否保留"。用户可见表达统一为 `partial` + 顶部一行「已取消（4/6 项完成）」。此修正不改变任何用户可见文案，只为消除前端"取消了但不知显示什么"的空档。

### 2.3 支线流程

| 支线 | 触发 | 行为 | 退出 |
| --- | --- | --- | --- |
| **单项重测** | 非 `running` 状态下点某卡「重测」或按 `1`–`6` | 该卡回 `pending → running`，应用转 `running`；其余 5 卡保持原值**不闪白、不清空**（PRD US-05.3）；完成后总分自动重算并标注"基于最近一次各项结果组合"（US-05.4） | 该项终态 → `done`/`partial` |
| **全部重测** | `done`/`partial` 下按 Enter 或点「重新检测」 | 清空全部 probe，新建 `runId` | 同主流程 |
| **直连对照** | 开启对照开关后开始 | 串行两轮：先代理侧、后直连侧，`maxConcurrency=1` 避免抢带宽污染差值。第二轮全程 C 区**保留第一轮结果**，顶部细进度条「对照轮 2/6」 | 两轮完成 → 出现 ComparePanel |
| **导出** | 任意有结果的终态 | 打开 ExportSheet（JSON / Markdown / 截图友好摘要 / 复制）。脱敏在导出时强制（`04-security.md` G1）；告知落盘路径 + 「打开所在目录」；断网可用（US-06.6） | 关闭回原状态 |
| **历史对比** | Header 点「历史」（P1 · US-09） | 右侧 Drawer：快照列表（时间/出网方式/总分/三项分）→ 选两条 → 差值视图，状态降级项高亮 | 关闭 Drawer |
| **看详情** | 任意 settled 卡 | 原地内联展开（宽屏）或全屏 Sheet（窄屏）；**不离开页面**，不打断其他仍在跑的项 | 关闭 / 切另一张 / Esc |
| **引擎断连** | SSE 中断 | 顶部非阻塞 Banner「与检测引擎的连接中断，正在重连（2/3）」；已渲染结果灰化只读 | 重连成功 → 恢复 `running`；3 次失败 → `failed` 并保留 `partial` 视图 |

### 3.2 probe 级：两条正交轴

**轴一 · Lifecycle（交互层独占）**

```
 ┌─────────┐  调度放行  ┌─────────┐  引擎下发 Verdict  ┌──────────┐
 │ pending │──────────▶│ running │──────────────────▶│ settled  │
 └────┬────┘           └────┬────┘                   └──────────┘
      │                     │
      │ 前置依赖失败 /       │ 用户取消 / 预算耗尽
      │ 轻量档不测           │
      └─────────────────────┴──────────────────────▶┌──────────┐
                                                    │ skipped  │
                                                    └──────────┘
```

`settled` 与 `skipped` 是终态；终态只能通过 `RETEST_ONE` 回到 `pending`。

**轴二 · Verdict（PRD §3.1 的 9 态，交互层只消费、不新增）**

| Verdict | 徽章中文（PRD 展示名） | 一句话语义 | 归层 | 三态族 | 用户动作 |
| --- | --- | --- | --- | --- | --- |
| `PASS` | 可用 | 达成成功条件，指标在"良"及以上 | — | 可用 | 无需动作 |
| `PASS_WITH_NOTE` | 可用（有说明） | 业务可用但有附注（如 API 401 = 缺 key、地区推断为非偏好区） | — | 可用 | 读附注 |
| `SLOW` | 可用但慢 | 事务完成但指标落"差"档（TTFB/吞吐/起播超阈） | 质量 | 受限-慢 | 换节点 / 降预期 |
| `BLOCKED_BY_POLICY` | 被策略拦截 | 地区限制 / 451 / 明确封禁页特征 | 平台 | 受限-策略 | 换落地地区 |
| `CHALLENGED` | 人机验证拦截 | 命中 Cloudflare/Akamai 挑战页或验证码容器 | 平台 | 受限-验证 | 换 IP / 换地区 / 等 1–5 分钟 |
| `RATE_LIMITED` | 被限流 | 429 或限流页特征 | 平台 | 受限-限流 | 稍后重试（**不归因于代理质量**；计 **55 分**，不参与 AI 分项封顶；界面标注「限流，网络可用」） |
| `TIMEOUT` | 超时 | 配置超时内未完成 | 出网 | 不可用 | 重测；持续则查代理 |
| `NET_FAIL` | 网络失败 | DNS/TCP/TLS 阶段失败（**含证书错误**） | 出网 | 不可用 | 查代理配置 / 核对系统时间 |
| `SKIPPED` | 未测 | 用户取消、前置依赖失败、时间预算耗尽 | — | 无 | 见 `skipReason`；**不计分** |

`NET_FAIL` 的 `subReason`（**已完成枚举定稿，7 个值，白名单外一律按 `no_network` 兜底并记日志**）：

| `subReason` | 判定依据 | 归因层（§6.7） | 文案要点 |
| --- | --- | --- | --- |
| `no_network` | OS 无默认路由 / 全部采样在 DNS 前失败 | 系统环境 | 「本机没有可用网络」 |
| `dns_pollution` | 解析结果异常 / 解析超时但 IP 直连可达 | 网络运营商 | 「域名解析被污染」 |
| `tcp_reset` | 连接被 RST 重置 | 代理 / 网络运营商 | 「连接被重置，链路中途被掐断」 |
| `tls_cert` | 证书校验失败 | 代理（MITM） / 系统环境（时间偏差） | 「证书校验失败，可能系统时间偏差或代理在解密流量」 |
| `timeout` | 配置超时内未完成握手或首字节 | 代理 / 目标服务 | 「长时间无响应」 |
| `ipv6_only` | 仅 AAAA 可达 / A 记录不可路由 | 系统环境 | 「只有 IPv6 通路，目标可能不支持」 |
| `sys_time` | 本地时间偏差导致证书有效期判定失败 | 系统环境 | 「系统时间不准，请先校准」 |

> `tls_cert` 与 `sys_time` 在归因上可能重叠：先报 `tls_cert`，若同时检测到时间偏差则 `subReason = sys_time` 优先，因为它是用户可自行解决的那一个。
> `tls_cert` 的文案必须独立于普通 `NET_FAIL`：「证书校验失败。可能是系统时间偏差，或代理正在解密流量。」并**只给「查看证书详情」，不给"忽略证书继续"**（PRD 第 6 章 #5 明文禁止）。

> **`truncated`（200 但响应被截断 / 劫持）不是 `subReason`**，它属于 PRD 第 6 章 #15「假通」：`verdict` 仍为已判定值，但在详情与结论层打「响应被截断」标记，不新增出网层枚举。

> **`UNSTABLE` 已被废除**：稳定性不是探测项状态，而是结论层的 **C6**（由 P6 采样成功率 / 连续失败次数推导）。前端不得出现 `UNSTABLE` 徽章。

**生命周期 × 结论的合法性**

| 组合 | 是否合法 | 说明 |
| --- | --- | --- |
| `running` + 任意 Verdict | ✗ | 有结论就不该还在 running |
| `settled` + Verdict（非 `SKIPPED`） | ✓ | 唯一合法落点 |
| `pending` + Verdict | ✗ | 无采样不能下结论 |
| `skipped` + Verdict | ✓ | 仅 `SKIPPED` 一种 |
| `skipped` + `SKIPPED` 且带业务 Verdict | ✗ | 不得同时给结论 |
| `settled` + `skipReason` | ✗ | 二者互斥 |

`skipReason` 与 `SKIPPED` 严格一对一（前端只渲染不判断）：`cancelled`（用户取消）、`upstream_failed`（前置依赖失败）、`budget_exhausted`（时间预算耗尽）。**无 `profile_omitted`**——档位不裁剪探测项（见 §3.3）。

> **`SKIPPED` 的呈现硬规则（PRD §3.1 强制规则 3）**：不得显示成 0 分、不得用通过色、必须显式标注「本次未测」；总分按已测项归一化，并在总分旁标注「N/6 项计入」。


### 3.3 应用级 `done` / `partial` / `failed` 判定

```
settledCount = count(lifecycle == settled)
skippedCount = count(lifecycle == skipped)
status = (skippedCount > 0 || settledCount < expectedProbeCount) ? 'partial' : 'done'
```

**`expectedProbeCount` 恒为 6（已定稿）**：档位**不裁剪探测项**，只压缩时长与流量预算（轻量档 = 6 × 更短的超时 + 更小的采样体量）。因此"轻量档永远 partial"这一风险不存在——`expectedProbeCount` 恒为 6，仍从配置读取以实现解耦，但不再有"某档位 N 项"的变体。`SKIPPED` 只由三类原因产生：用户取消、前置依赖失败、预算耗尽，**不含"档位跳过"**。

**`failed`（应用级）触发，任一成立：**

1. 引擎健康检查失败（进程不可达 / 端口不通 / 握手失败）
2. 本机网络不可用（OS 无默认路由，或 P6 全部采样在 DNS 阶段即失败）
3. **≥5 项归一到同一层同一类失败**（如全部 `NET_FAIL` 且失败阶段均为 TCP）→ 判为"代理配置问题"
4. SSE 断连重试 3 次仍失败

> 规则 3 是"代理端口填错"的典型指纹。此时**不要**把 6 张红卡甩给用户，应折叠为一条根因说明 + 一个「去修改代理」按钮。

### 3.4 非法迁移（reducer 与 UI 双重阻断）

| # | 非法迁移 | 危害 | 阻断方式 |
| --- | --- | --- | --- |
| 1 | `pending → settled` | 跳过采样直接给结论 = 假数据 | reducer 丢弃无 `startedAt` 的结论事件 |
| 2 | 终态 → `running`（非 `RETEST`） | 静默覆盖已得信息 | 仅接受 `RETEST_ONE(id)` / `RETEST_ALL` |
| 3 | `done → partial` 无重测 | 完整度倒退 | 完整度仅在 `running → 结束` 时计算；`done` 拒绝无 RETEST 的状态写入 |
| 4 | `running` 中重复 `START` | 两个 run 并发，互相抢带宽，数字失真 | `running` 下 `START` 为 no-op；主按钮此时是「取消」 |
| 5 | 改配置后直接用新配置展示旧结论 | 结论与配置错配，严重误导 | 改任一配置 → 立刻 `configuring` + **阻断式提示**（不是弱化文字）：「配置已修改，当前结果为旧配置产生」+ 三个选择〔立即重新检测 / 仅查看旧结果 / 取消修改〕；选「仅查看」则旧结果永久带灰底「旧配置结果」标注。详见附录 C-5 |
| 6 | 直连对照两轮并发 | 抢带宽，差值无意义 | 对照模式强制 `maxConcurrency=1`，第二轮显式标为「对照轮」 |
| 7 | 取消后引擎仍推事件 | 幽灵更新、状态闪烁 | run 带 `runId`，取消即递增 `epoch`，丢弃旧 `runId` 全部事件 |
| 8 | 同时多个 `RETEST_ONE` 在飞 | 破坏并行调度的基线条件 | 同一时刻仅允许 1 个重测；其余按钮临时不可用 + tooltip「等待当前重测完成」 |
| 9 | `blocked` 文案复用 `failed` 文案 | 抹掉产品核心差异化 | 文案映射表强制分离（§6），组件只能用 Verdict 取文案，禁止自行 switch |
| 10 | `skipped` 参与分数计算或渲染通过色 | 违反 PRD US-04.3 | `verdict.ts` 对 skipped 返回 `null` 分数；UI 灰化 + 「本次未测」 |
| 11 | 校验未过仍发请求 | 引擎收到垃圾输入，错误归因混乱 | 允许点按钮，但点击即拦截：不发请求、聚焦输入框、行内报错（§7.2） |
| 12 | 未脱敏导出 | 违反 `04-security.md` G1 | 导出统一走脱敏函数；`RawJsonViewer` 复制同理 |

## 4. 实时反馈策略

### 4.1 全量 vs 局部：一律局部

**禁止**任何"重渲染整页"的实现。每个 probe 有独立事件通道，UI 按 `probeId` 做定向 patch。

```
引擎 ──SSE──▶ ProbeStream ──(dispatch by probeId)──▶ ProbeStore[pid]
                                                        │
                        ┌───────────────────────────────┼───────────────┐
                        ▼                               ▼               ▼
                  ProbeCard(pid)                  ScoreStrip       VerdictCard
                  仅订阅自己的 slice               聚合订阅         聚合订阅
```

- `VerdictCard` 与 `ScoreStrip` 订阅**聚合选择器**（settled 项集合），只有集合变化才重算；
- 高频的"当前速度"只驱动 `ProbeCard` 内单一文本节点 + `ProbeSparkline`，不触达上层；
- 数组/对象引用稳定：`ProbeStore` 用 per-id 不可变切片，避免父级 diff 扩散。

### 4.2 刷新频率（三层节流）

| 层 | 频率 | 理由 |
| --- | --- | --- |
| 引擎采样推送 | **4 Hz**（`probe.sample` 每 **250ms** 聚合一帧；引擎内部 100ms tick 只供算法自用） | 与 `06-engine-design.md` §8.1 定稿一致；满足 PRD US-03.2「≤500ms」并留一倍余量 |
| 图表绘制 | 合并到 rAF，上限 10 Hz，掉帧则丢点不补 | 避免 layout thrash；曲线形态不受影响 |
| 数字文本（Mbps / ms / %） | 2 Hz（500ms） | 数字跳太快读不住；加等宽数字防抖动 |
| `aria-live` 播报 | **仅状态变化时**（pending→running→settled），进度不播 | 否则屏幕阅读器被 250ms 一次的信息淹没 |
| 总耗时计时器 | 1 Hz | 秒级刷新足够 |

> 采样帧的 `mbps` 已是引擎侧 250ms 聚合值，**前端不得再对 `mbps` 做二次平均**（会掩盖掉速）；只做显示节流，不做数据加工。`mbpsRaw` 仅进详情曲线，不进卡片主数字。

> 用户取消后 **≤500ms 内必须停止刷新**（PRD US-05.1）：取消即刻 `epoch++`，前端丢弃后续事件并不再写入 store，UI 立即切换为只读态。

### 4.3 进度表达：三类探测项用三种进度

不存在"统一进度条"。用错类型会比没有进度更糟。

| 探测项类型 | 进度表达 | 展示示例 | 理由 |
| --- | --- | --- | --- |
| **吞吐类**（P1、P2） | **时间进度为主 + 字节为辅** | `▰▰▰▰▰▱▱ 4.2s / 8s · 已收 32.4 MB` | 时间预算固定，用户最想知道"还剩几秒"；字节总量固定反而会因降速而"进度倒退" |
| **可达类**（P3、P4、P5） | **阶段进度（5 段 stepper）** | `DNS ✓ → TCP ✓ → TLS ✓ → HTTP ⟳ → Body` | 用户能看到"卡在 TLS"这类有价值信息，这本身就是诊断结果 |
| **采样类**（P6） | **样本进度（n/N 个点）** | `▰▰▰▱▱ 3/5 次采样 · 丢包 0%` | 离散采样，用次数天然诚实 |
| **全局** | **已完成项数 / 期望项数** | `4 / 6 项完成` | 并行任务唯一诚实的全局进度；**不要**用加权百分比假装精确 |

统一约束：
- 进度条必须有 `role="progressbar"` + `aria-valuetext`（读作"已测 4.2 秒，共 8 秒"），而非纯视觉；
- 不确定总时长时用**不定态**（indeterminate）条纹，绝不伪造百分比；
- 任一进度不得因重算而视觉回退（除重测该单项）。

### 4.4 `running` 期间控件可用性

| 控件 | 状态 | 说明 |
| --- | --- | --- |
| 取消检测 | **可用，始终可见** | PRD US-05.1 硬要求；Esc 等效 |
| 单项重测（已 settled 项） | **可用**（全局仅 1 个在飞） | 核心效率特性 |
| 单项重测（running/pending 项） | 不可用 | 避免同项双跑 |
| 展开详情（已 settled 项） | **可用** | 边测边看证据 |
| 展开详情（未 settled 项） | 不可用 + tooltip「检测完成后可查看」 | 避免展示半截数据 |
| 模式 / 地址 / 档位 / 对照开关 | **不可用**（配置区折叠为只读摘要） | 运行中改配置语义不明；先取消再改 |
| 导出 | 不可用（无完整结果） | 取消/完成后可用 |
| 历史 Drawer | 可用 | 只读，不干扰 |
| 主题切换 | 可用 | — |
| 滚动 | 可用，绝不锁滚动 | 用户要能读已完成项的详情 |
| 快捷键 `1`–`6` | 可用（作用于已 settled 项） | — |
| 快捷键 `Enter` | 不触发新 run（等同于取消？**不**） | `running` 下 Enter 为 no-op，防止误触清空 |

> 一个反直觉但重要的决定：**`running` 状态下不锁配置区，而是折叠**。折叠保留"我看到我用的是什么配置"的可核对性，锁定则会让人怀疑"是不是配置有问题才不让我改"。

## 5. 四类状态：文案与交互

统一规则：
- 每条错误文案 = **发生了什么 + 这意味着什么 + 下一步做什么**，三段缺一不可；
- 不出现裸技术栈错误（`ECONNREFUSED` 只能出现在证据/JSON 里，不进主文案）；
- 不甩锅、不承诺（"绝对不会被风控"是禁令，见 §6.5）。

### 5.1 空状态（Empty）

| 位置 | 文案 | 交互 |
| --- | --- | --- |
| C 区（idle） | 主：**先确认出口，再开始体检**<br>副：留空即走系统默认出网（当前 TUN 接管时等同直连语义）。<br>按钮：`开始检测 ⏎` | 点按钮直接开跑 |
| E 区空态卡 | 卡片显示编号与名称 + 一行「将测什么」：<br>P1「下载 40 MB 大文件，看真实吞吐」<br>P3「打开 ChatGPT 首页，判断是否被人机验证拦截」<br>P6「5 次连通采样，看会不会掉线」 | 不可展开 |

### 5.2 加载（Loading）

| 场景 | 文案 | 交互约束 |
| --- | --- | --- |
| 出网方式识别中 | 徽章「识别中…」，≤1s 后落定 | 不阻塞开始按钮（PRD US-01.1） |

| 详情展开（本地已有数据） | 无 loading（数据在内存） | 立即展开，200ms 内完成 |
| 导出生成中 | 按钮内联 spinner + 「正在生成报告…」 | 可取消；生成完 Toast 告知路径 |
| 历史快照读取 | 列表骨架 ×3 | ≤300ms（本地 SQLite/文件），超时降级为「读取失败，可重试」 |

### 5.3 错误（Error）

| 场景 | 主文案 | 副文案（意味着 / 下一步） | 交互 |
| --- | --- | --- | --- |
| 地址格式错 | 「代理地址格式不正确」 | 「应为 `协议://主机:端口`，例如 `socks5h://127.0.0.1:7890`」 | 行内红字 + 输入框聚焦 + 按钮不 disabled |
| 端口缺失 | 「缺少端口号」 | 「HTTP 默认 8080、SOCKS 常见 7890，请确认你的客户端监听端口」 | 同上，光标定位到行尾 |

| 引擎中途断连 | 「与检测引擎的连接中断」 | 「正在重连（2/3）。已完成的 4 项结果已保留，重连后可继续。」 | 非阻塞 Banner，结果灰化只读 |

| 导出失败 | 「报告写入失败」 | 「目标目录可能无写入权限。可改用『复制到剪贴板』。」 | Toast + 备用动作 |

### 5.4 降级（Degraded）—— 必须让用户看见

安全文档 G4 要求「任何降级都不得静默」。以下情形**强制**在对应探测卡与报告头出现降级标记：

| 降级情形 | 卡片标记 | 文案 |
| --- | --- | --- |
| 轻量档未含该项 | 虚线灰卡 · `本次未测` | 「轻量档不包含此项。切换『深度』可完整检测。」 |
| 证书校验被跳过 | ⚠ 标记 | 「本次跳过了证书校验，结果可能受中间人影响，不可作为安全结论。」 |
| 使用明文 HTTP 代理 | ⚠ 标记 | 「代理链路为明文 HTTP，凭据与内容在本地到代理之间未加密。」 |
| 疑似响应被劫持/截断 | ⚠ 标记 | 「响应内容与预期不符（疑似被中间设备改写），结论仅供参考。」 |

## 6. 结论解释设计（核心）

产品的差异化全在这里：**能不能把"能连但不能用 AI"讲清楚**。

### 6.1 结论的四段式结构

```
① 一句话结论   —— 能不能顺畅用 AI（≤ 20 字，不含数字）
② 卡在哪一层   —— 出网 / 质量 / 平台（三选一，可多选但要有主次）
③ 下一步做什么 —— ≤3 条，动词开头，可直接执行
④ 支撑句       —— 一行证据摘要，可展开为完整推理
```

示例：

> **能用，但 ChatGPT 会撞人机验证**
> 卡在：平台风控层
> → 换一个落地地区（当前节点所在地区风控较严）
> → 或换一个出口 IP 后重测 P3
> 支撑：`chatgpt.com` 返回 403 + Cloudflare 挑战页特征；Gemini 正常；API 端点 401（可达）。

### 6.2 三层漏斗（`verdict.ts` 的判定顺序）

判定必须**自上而下短路**，先回答最底层的问题。上层不通时，下层结论一律不展示（避免"链路断了还告诉你 ChatGPT 被风控"这种胡话）。

```
L1 出网层
  问：有没有任意一条国际链路成功？
  看：P6 至少 1 次成功？ P1 是否至少完成 TCP+TLS？
  ├─ 全失败 ──▶ 结论类型 A：完全出不去（不再评估 L2/L3，把 P3–P5 标为 skipped:upstream_failed）
  └─ 有成功 ──▶ 进入 L2

L2 质量层
  问：通是通了，能不能"顺畅"用？
  看：P1 吞吐是否达阈值、P2 起播耗时、P6 成功率与抖动
  ├─ 达标 ──▶ 进入 L3
  └─ 不达标 ──▶ 记为「质量受限」，**但仍继续评估 L3**
                （慢 ≠ 不可用，可能 AI 网页照样能开）

L3 平台层
  问：AI 目标放不放行？
  看：P3 / P4 / P5 的 Verdict
  ├─ 全部 PASS / PASS_WITH_NOTE ──▶ 全绿
  ├─ 存在 CHALLENGED / RATE_LIMITED ──▶ 结论类型 B
  └─ 存在 BLOCKED_BY_POLICY ──▶ 结论类型 C
```

**最终结论 = 最严重的层级 + 其余层级作为支撑。** 优先级：L1 失败 > L3 拦截 > L2 劣化 > 全绿。

### 6.3 模板库（前端按 `verdict.ts` 返回的 `template` 键渲染，文案由文案表提供）

**T1 · 全绿**
> 结论：**可以顺畅用 AI**
> 定位：无阻塞层
> 下一步：无需动作。想更稳可开「深度检测」跑 30 秒长采样。
> 条件：P1 达标 && P3/P4/P5 均 PASS 或 PASS_WITH_NOTE && P6 成功率 100%

**T2 · 链路通，被 CDN 风控拦截（最高频场景）**
> 结论：**链路是通的，但 ChatGPT 被人机验证挡住了**
> 定位：平台风控层
> 下一步：
> → 换一个落地地区（部分地区风控更严），重测 P3
> → 或换一个出口 IP 再试（同一 IP 频繁访问会持续被挑战）
> 支撑：`chatgpt.com` 返回 403 且命中 Cloudflare 挑战特征；同链路上 Gemini 正常、API 端点可达 401。
> 用户可读的解释句：**「路通了，门锁了」**——网络没问题，是对方的安全策略在拦。
> 条件：P6 成功 && P1 达标 && P3 = CHALLENGED

**T3 · 链路通，但落地地区被拒**
> 结论：**网络完全正常，但这个地区的 IP 被服务方拒绝**
> 定位：平台风控层（地区策略）
> 下一步：
> → 把节点换到服务支持的国家/地区
> → 不用反复重试，同地区重试不会改变结果
> 支撑：`gemini.google.com` 返回 451 / 命中地区不可用页特征；`chatgpt.com` 同样被拒。
> 关键交互：**明确告诉用户"重试无用"**，否则用户会反复点重测。
> 条件：P3、P4 均 BLOCKED_BY_POLICY

**T4 · 带宽偏窄，但 AI 可用**
> 结论：**AI 能用，但带宽偏窄，上传大文件/长对话会明显慢**
> 定位：质量层
> 下一步：
> → 日常问答可用，长文档上传建议分批
> → 若需视频/大文件，换更高带宽节点
> 支撑：吞吐 12.4 Mbps（p50），TTFB 820ms；六项 AI 目标全部放行。
> 条件：P1 = SLOW 或 degraded，且 L3 全绿

**T5 · 完全出不去**
> 结论：**当前配置下出不去，任何国际服务都连不上**
> 定位：出网层（最先该修的就是这里）
> 下一步：
> → 确认代理客户端正在运行，且端口与所填一致
> → 若留空走系统代理，切到「直连」跑一次，判断是代理坏了还是网络本身断了
> → 若直连也不通，先修本机网络
> 支撑：6 项全部在 TCP 阶段失败；DNS 阶段正常（说明本地解析可用）。
> 条件：L1 全失败

**T6 · 能连但极不稳定（隐藏的高价值结论）**
> 结论：**能连上，但会间歇性掉线，不适合长连接/API 任务**
> 定位：质量层（稳定性）
> 下一步：
> → API 场景建议加重试与超时；当前链路出现连续 3 次失败
> → 换节点或换时段再测，确认是线路抖动还是偶发
> 支撑：5 次采样成功 3 次，抖动 186ms，最长连续失败 3 次。
> 条件：P6 采样成功率 < 阈值或存在连续失败 → 结论层判为 **C6（不稳定）**（`UNSTABLE` 不是探测项状态，见附录 C-1）

**T7 · 直连对照的专属结论**
> 结论（直连也不通）：**直连同样不可达，属预期结果**
> 副：这不是代理的问题。所测服务在当前地区本就无法直连。
> 结论（代理通、直连不通）：**代理确实起作用了**
> 副：开代理 Δ 吞吐 +38.2 Mbps，AI 可用性由「被拦截」变为「正常」。

### 6.4 反直觉结果的专门规则（极易被误读，必须硬编码）

| 结果 | 用户第一反应 | 界面必须做的事 |
| --- | --- | --- |
| `api.openai.com` 返回 **401** | 「失败了！」 | 徽章 = `可用 · 无密钥`（PASS_WITH_NOTE），并在卡片正面直接写「401 表示服务在线，只是没带 API Key —— 这正是网络通的证据」。**绝不可**用错误色。 |
| `403` | 「被墙了」 | 区分：命中挑战特征 → `被人机验证拦截`；纯 403 无特征 → `被拒绝（原因未识别）`，并提示"可能是 UA/地区/风控，证据见详情" |
| `429` | 「代理坏了」 | `被限流`，副文案「你的出口 IP 短期请求过多。等 1–2 分钟或换 IP，不是配置问题。」 |
| 全部 `TIMEOUT` | 「网断了」 | 若 DNS 正常而 TCP 全超时 → 文案偏向「连接被丢弃，常见于代理端口错误或防火墙拦截」，而不是"网络断了" |
| 证书错误 | 「忽略掉就行」 | **不提供"忽略证书继续"的一键按钮**。文案：「证书校验失败。可能是系统时间偏差或代理在解密流量。请先核对系统时间；如果这是你自己搭的代理，检查它的证书配置。」 |
| 单项 `SLOW` 但其他全绿 | 「总分被拉低了」 | 总分旁标注「受 P1 带宽影响」，并在结论里说明"不影响 AI 可用性" |

### 6.5 文案禁令

- ✗ 「您的网络非常安全」/「绝对不会被检测到」——不为上游风控背书（PRD §1.4）
- ✗ 「代理有问题」用在**直连模式**下（PRD US-10.2）
- ✗ 把 `blocked` 说成「失败」而不给可执行动作
- ✗ 用「异常」「错误」作为唯一描述（无信息量）
- ✗ 出现「请稍候」而无阶段名
- ✗ 展示完整响应体、完整 IP、完整凭据（脱敏见 §7.4）

### 6.6 三态收敛与视觉通道（对齐用户研究 §7 「三态不是红绿」）

**先钉一个容易做错的前提：本产品有两条各自独立的三值轴，不可合成一条。**

| 轴 | 适用探测项 | 三值 | 回答的问题 |
| --- | --- | --- | --- |
| **A 轴 · AI 可用性三态** | P3 ChatGPT、P4 Gemini、P5 API | 可用 / 受限 / 不可用 | 平台放不放行 |
| **B 轴 · 速度三值** | P1 下载、P2 视频起播（P6 用成功率另述） | 够用 / 勉强 / 不够 | 够不够开视频、传文件 |

`SLOW` **只属于 B 轴**，不得进入 A 轴。否则"慢"与"被墙"又被压回同一个「受限」里，恰好复现了本产品要打败的"把慢说成不可用"的谎报。（"不稳定"同理不进 A 轴，它以结论 C6 的形式出现在结论层，见附录 C-1。）

**A 轴三态收敛表**（收敛只发生在 `verdict.ts`，组件不得自行归类）：

| 三态 | 收敛自 | 用户语 | 视觉通道（**至少满足 2 个维度，颜色最多占 1 个**） |
| --- | --- | --- | --- |
| **可用** | `PASS`、`PASS_WITH_NOTE` | 正常 / 可用（无密钥） | ① 形状：实心圆点 ② 位：阶段条走满 ③ 文案：「可用」 |
| **受限** | `CHALLENGED`、`BLOCKED_BY_POLICY`、`RATE_LIMITED` | 能连但被拦 | ① 形状：**半填充圆点 / 缺口圆环**（区别于叉）② 位：阶段条走到 HTTP 后中断 ③ 文案：「被人机验证拦截」「被地区策略拦截」「被限流」+ **必须带动作** |
| **不可用** | `NET_FAIL`（含证书错误，用 `subReason=tls_cert` 区分）、`TIMEOUT` | 连不上 | ① 形状：叉 / 断环 ② 位：阶段条停在 DNS 或 TCP ③ 文案：「未连通」+ 五类归因之一 |

**B 轴三值**（用于 V3 速度裁决，不参与 A 轴着色）：

| 三值 | 收敛自 | 用户语（必须绑业务语义） |
| --- | --- | --- |
| 够用 | `PASS` | 「够开 1080p 视频，够传大文件」 |
| 勉强 | `SLOW` | 「能问答，长文档上传会明显慢」 |
| 不够 | `SLOW`（吞吐/起播低于下限档） | 「开视频会卡，建议只做文字对话」 |

两轴在首屏是**并列呈现**的（V2 用 A 轴，V3 用 B 轴），一红一绿并不矛盾——"ChatGPT 被拦（受限）+ 速度够用"是极常见的真实组合。

**「A 受限 + B 够用」是标准复合态，不是边缘情况，必须按标准布局设计。**

这是本产品最需要举证的一个场景：用户要对客服/同事说的原话就是"我网速是好的，是它拦我"。因此：

| 硬规则 | 具体要求 |
| --- | --- |
| **B 轴的好消息不得被 A 轴的失败吞掉** | A 轴判为「受限」或「不可用」时，V3 的速度结论**照常展示、照常给档位**，不得折叠、置灰、或降级为"因 AI 不可用，速度未评级" |
| **V1 一句话裁决必须是两轴的合成，而不是第三种状态** | 合成规则：`A 轴结论` 为主体（AI 能不能用），`B 轴结论` 作为从句保留（网络本身够不够）。例：「ChatGPT 被人机验证拦截；网络本身够开 1080p 视频」——一句话里两个轴都在，且**互不抵消** |
| **视觉权重 A > B，但可见性 A = B** | 首屏不给 B 轴做小一号的弱化处理（弱化会被读成"不重要/不可信"）；两轴各自占独立的行，各自带自己的徽章 |
| **复合态的文案模板** | 见 §6.3 T3；模板必须显式写出"网络正常"这一判断，而不是让用户从"只有 AI 卡是红的"自行推断 |

反例（禁止）：把 A 轴结论写成「当前网络不可用」——这句话同时否定了用户已经花钱买到的带宽，是**事实错误**，也是 C 类用户流失的首要原因。

**「受限」内部还有三个子变体，必须再区分一次（PRD §3.1 强制规则 + 第 6 章 #7）**

PRD 明文禁止把 `CHALLENGED` 与 `BLOCKED_BY_POLICY` 合并为"被墙"，因为**处置方式完全不同**。三态收敛不能成为新的压扁工具，因此受限带内必须有第三个区分维度：

| 子变体 | 收敛自 | 徽章中文 | 处置方向 | 区分手段（与同带其他变体的差异） |
| --- | --- | --- | --- | --- |
| 受限-验证 | `CHALLENGED` | 人机验证拦截 | 换 IP / 等 1–5 分钟 | 动作前缀「换出口 IP」；旁注含「页面能到达」 |
| 受限-策略 | `BLOCKED_BY_POLICY` | 被策略拦截 | 换落地地区 | 动作前缀「换落地地区」；旁注含地区名 |
| 受限-限流 | `RATE_LIMITED` | 被限流 | 稍后重试 | 动作前缀「等 1–2 分钟」；旁注明确「不是配置问题」 |
| 受限-慢 | `SLOW` | 可用但慢 | 换节点 / 降预期 | 归 **B 轴**，不占 A 轴徽章（见下表） |

实现建议：受限带内用**同一个图形母题 + 不同的内部符号/分隔线**，而不是三种颜色。这样既保住带级识别（"这条路被拦了"），又保住变体识别（"被谁拦的"）。

**「受限」必须有独立的视觉通道，这是本产品最容易被做错的一处。**
理由：`CHALLENGED` 的语义是"网站是活的，它在拦你"——它与"连不上"指向完全相反的用户动作（换 IP vs 查配置）。若二者共用一种视觉，界面就在说谎。
可实现的区分手段（任选 ≥2）：填充形态、位置/进度、文案首字（「被」vs「未」）、存在或缺失的旁注行、图形轮廓（圆 vs 断环 vs 叉）。

**通道分层：位置通道只服务证据层，不得承载判断层（纠正一条我早先的错误假设）**

| 层级 | 服务对象 | 允许的通道 | 理由 |
| --- | --- | --- | --- |
| **判断层**（首屏结论 / V2 徽章三态） | C 类用户：不解析技术语义，只看"行不行" | 形状 + 文案首字（可 / 受 / 不）+ 旁注行存在性 + 颜色（占 1） | 这四个通道**无需任何前置知识**即可解码 |
| **证据层**（详情页阶段条 / 瀑布） | A、B 类用户：愿意看"卡在哪一层" | 位置 / 进度 / 阶段名 / 状态码 | 位置通道要求"懂阶段顺序"，属专业读者的解码成本，不能外推给 C 类 |

推论（硬约束）：**首屏裁决不得依赖"阶段条停在 DNS 还是 HTTP"来传达三态**。位置通道在首屏只能作为辅助冗余；把它从界面上拿掉，三态仍须可辨。ui-designer 已按此裁定「缺口圆环 90° 缺口」——缺口是形状通道，不是位置通道。

**三态的表达禁止**：
- ✗ 只用颜色区分三态（色盲不可辨，灰度打印不可辨）；
- ✗ 把「受限」渲染成失败色的同时不给动作——等于说"坏了"，实际是"被挡了"；
- ✗ 在首屏出现「受限」却不写被什么挡（必须写「被人机验证拦截」而非「异常」）；
- ✗ 三态与分数耦合（`受限` 不等于低分；地区拦截可以是 0 丢包、高带宽、满分质量层）；
- ✗ 把 B 轴的「不够」渲染成 A 轴的「不可用」。


### 6.7 失败态归因（对齐研究 §5.2「失败态是一等公民」+ PRD 第 7 章 #771）

应用级 `failed` 与全红场景**禁止**只给一句 toast。必须输出三件事：

```
① 责任方归因（PRD 五类：用户 / 代理 / 目标服务 / 系统环境 / 网络运营商，必须选边）
② 一条具体动作（可执行，非"建议优化网络"）
③ 一条"排除法"建议（把 5 个可能缩到 1 个的最快一步）
```

**归因是五类，不是三类。** PRD 第 7 章明确要求「同一个 `NET_FAIL` 在无网络 / DNS 污染 / 证书错误 / IPv6-only / 系统时间错 中的文案必须完全不同」。若只做"本地/代理/目标"，这五种 `NET_FAIL` 会被压成同一句"网络失败"，正好违反 PRD 强制规则 1（禁止不带归因的状态名）。

| 责任方 | 判定线索（均落到 `NET_FAIL`） | 动作 | 排除法建议 |
| --- | --- | --- | --- |
| **用户**（配置） | 代理端口填错 / 未填端口 / 选错协议 / `socks5://` 导致本地 DNS 污染 | 「核对端口与客户端是否一致，或改用 `socks5h://`」 | 「清空地址走系统代理再测一次」 |
| **代理** | ≥5 项同层同阶段失败 / TCP 被拒 / 407 代理认证失败 / 端口无监听 | 「确认代理客户端已启动，端口一致」 | 「点『直连』重测：直连正常即证明是代理配置」 |
| **目标服务** | L1 已通过 + 目标返回 5xx / 451 | 「稍后重试，或换落地地区」 | 「同链路其他目标正常即为目标侧问题」 |
| **系统环境** | 系统时间偏差 / OS 无默认路由 / 引擎进程异常 / IPv6-only 而目标仅 IPv4 | 「校准系统时间」或「重启 ProxyLens」 | 「切到直连跑一次：直连也不通则问题在本机」 |
| **网络运营商** | DNS 解析到可疑地址 / 中途丢包且多目标同时受累 / 劫持疑似 | 「换 DNS 或换网络环境后重测」 | 「换一条网络（如手机热点）对比即为运营商侧问题」 |

映射到 UI：`FailureAttribution` 组件的 `party` 取这五个值之一；**`party` 必填，无「未知」选项**——宁可给"最可能方 + 置信度低"的措辞，也不给空归因。

**「必填五选一」有一个已知风险：它会把不确定的情况硬塞进一个错误的责任方（false attribution）。** 一个把责任推给"目标服务"的界面，会让用户去换节点；如果真实原因是本地时间偏差，用户换了三次节点后就会不再相信这个产品。因此在这一条上补一个受控逃生口，它**不是**「未知」，而是一个**带义务的中间态**：

```
attribution.status = 'confirmed' | 'pending'
```

| 状态 | 何时用 | 界面义务 |
| --- | --- | --- |
| `confirmed` | 有明确判定线索（上表任一列可精确命中） | 正常输出五类之一 + 动作 + 排除法 |
| `pending` | 线索冲突或证据不足，五类都可能 | ① `party` 仍必须填**最可能方**（UI 上不显示为结论，只显示为"可能是"）② **必须**附一条「一条命令/一次点击就能定论」的排除动作 ③ 文案固定形如：「暂时无法确定问题在哪一侧。先做这一步就能定论：〔切到直连重测〕」 |

三条硬约束（防止 `pending` 退化为偷懒兜底）：
1. **`pending` 不得作为默认值**——引擎未给结论时，前端按"证据不足"降级为 `pending` 并在内部日志记一笔，不得静默归到某一方。
2. **`pending` 不许省掉动作**。没有排除动作的 `pending` 等于"未知"，直接违反 PRD 强制规则 1，测试用例判失败。
3. **自测集里 `pending` 占比 > 15% 视为判定逻辑未完成**，不是文案问题——须回到引擎补判定线索，不允许靠改文案消化。


**每条红灯必须配一个动作**（研究 §7 硬要求）。红灯的四种动作类型，文案必须落在其中之一：

| 动作类型 | 文案样例 | 适用 |
| --- | --- | --- |
| 换节点 / 换地区 | 「换一个落地地区后重测」 | 平台风控、地区拦截 |
| 换时段 / 重试 | 「等 1–2 分钟后重测，多半是短时限流」 | 429、偶发抖动 |
| 查配置 / 找自己 | 「核对代理端口是否与客户端一致」 | 出网层失败 |
| 无需处理 | 「这是服务方的正常策略，你的网络没有问题」 | 451 地区限制且用户不打算换区 |

「建议优化网络」「网络质量较差」一律**不算动作**。

### 6.8 结果档位 A–E 的呈现（PRD §3.2 强制可见）

PRD 锁死 5 级档位，且要求**在 UI 与导出报告中显式可见**。档位是"分数的人话翻译"，不能只有分数。

| 档位 | 区间 | 展示词 | 首屏呈现（V1 裁决的行尾） |
| --- | --- | --- | --- |
| A | 85–100 | 优 | 「可以顺畅用 AI · 优」 |
| B | 70–84 | 良 | 「可以用 AI · 良」 |
| C | 55–69 | 可用 | 「能用，但体验打折 · 可用」 |
| D | 30–54 | 较差 | 「勉强可用，建议换线路 · 较差」 |
| E | 0–29 | 不可用 | 「当前不可用 · 不可用」 |

呈现规则：
1. **档位与三态是两个维度，不得互相替代**。可能出现「AI 可用性 E 档」而「速度 A 档」——这正是 C3「能连但用不了 AI」的典型形态，必须在界面上同时成立。
2. 总分给档位，三个分项分**也各给档位**（PRD 要求分项分与总分都在报告中显式可见）。
3. 档位词（优/良/可用/较差/不可用）与三态词（可用/受限/不可用）**存在字面重叠，是刻意保留的**：用户对"可用/不可用"的语义直觉最强。但二者视觉位不同——档位挂在分数旁，三态挂在探测卡徽章上，不得混用同一样式。
4. `SKIPPED` 占多数导致归一化基数过小时，档位旁必须标注「基于 N 项」；N < 3 时档位降级为「样本不足，暂不评级」，**不给出可能误导的档位**。
5. 档位定义的变化（若 `06` 调整区间）必须同时改 `verdictCopy.ts` 与导出的 Markdown 表头，不允许只改一处。
6. **`RATE_LIMITED` 计 55 分（落 C 档「可用」），且不参与 AI 分项封顶**（已定稿）。理由是自伤性：用户连测两次必然撞 429，若按 0 分计，档位会凭空掉两档，直接破坏 PRD US-04「重测一致性」。界面义务有三条——① 徽章写「被限流」② 旁注必须写明「**限流，网络可用**」（把"不是你的网络坏了"说在用户看到分数之前）③ 归因固定为**目标服务**，禁止归因代理或本地配置。导出报告同样标注，不得只在 UI 上写。

## 7. 代理模式切换的交互细节

### 7.1 三选一：语义显式，不让人靠"留空"猜

```
出口方式   ┌──────────┬──────────┬──────────┐
           │ 系统代理 │ 自定义   │ 直连     │   ← segmented，单选，默认第 1 项
           └──────────┴──────────┴──────────┘

[系统代理] 地址输入框**可编辑、默认空**（不是 disabled）。占位「留空即走系统默认出网路径」
           下方常驻说明块（不是 tooltip）：
           ┌────────────────────────────────────────────────────┐
           │ 当前出网方式：TUN 或全局接管                         │
           │ 已检测到环境变量 HTTPS_PROXY=http://127.0.0.1:61713 │
           │ 留空 ≠ 直连。它走操作系统默认路径，可能被 TUN 接管。 │
           └────────────────────────────────────────────────────┘
           ↑ 三处提示（placeholder / 常驻说明块 / HeaderBar 实测徽章）是
             唯一的认知纠偏手段。禁用输入框属于"用限制解决困惑"，
             会把手动代理路径锁死，使 M6、S4 与 A 类用户被排除在外。

[自定义]   输入框 enabled 并自动聚焦，占位 `socks5h://127.0.0.1:7890`

[直连]     输入框隐藏，出现独立警示块（视觉权重高于说明块）：
           ┌────────────────────────────────────────────────────┐
           │ 直连模式将忽略系统代理与环境变量，直接出网。         │
           │ 用于对照实验。多数网络下 AI 服务会被拦截，属预期。   │
           └────────────────────────────────────────────────────┘
```

**为什么必须常驻说明块**：PRD §1.5 把"留空 = 直连"列为易错边界，误解的后果是拿到一份错误的对照结论。tooltip 需主动悬停，不构成"不得假设"的保障。

**环境变量必须单独暴露**：需求基线 §4 记录当前环境存在 `HTTP_PROXY/HTTPS_PROXY` 注入，而 `scutil --proxy` 显示系统代理未开启。若界面只说"系统代理：未开启"，用户会对结果完全不信任。故出网方式为六值枚举（PRD US-01.2），多来源同时存在时全部列出：

| 枚举 | 徽章文案 | 附加行 |
| --- | --- | --- |
| `system_http` | 系统代理（HTTP） | `127.0.0.1:8080` |
| `system_socks` | 系统代理（SOCKS） | `127.0.0.1:7891` |
| `tun` | TUN 或全局接管 | 「系统代理未单独开启，流量可能被 TUN 接管」 |
| `env` | 环境变量代理 | `HTTPS_PROXY=http://127.0.0.1:61713` |
| `direct` | 直连 | — |
| `unknown` | 无法识别 | 「将按系统默认路径尝试，结果可能不代表任何明确配置」 |

冲突时：徽章显示主来源，附加行列出冲突项 + 「存在多个代理来源，实际路径以上述优先级为准」。**不提供"帮我改系统设置"按钮**（PRD §1.4：只诊断不处置）。

### 7.2 自定义地址校验：分级而非二值

`blur` 时与输入后 300ms 防抖校验。**「开始检测」永不 disabled**（PRD US-01.1：零输入可点；且 disabled 按钮无法解释原因）。

| 级别 | 触发 | 呈现 | 阻止开始 |
| --- | --- | --- | --- |
| `error` | 协议不在白名单 / 缺主机 / 端口非数字或越界 1–65535 / 含空格 | 行内错误 + 输入框错误态 | **是**（点击时不发请求、聚焦输入框、保持错误态） |
| `suggest` | 未写端口（如 `socks5h://127.0.0.1`） | 「缺少端口，常见 7890」+「填入 7890」按钮（不自动改） | 是（无端口无法连接） |
| `warn` | 公网主机用 `socks5://`（DNS 本地解析）/ 端口非典型 / 域名为 SOCKS 目标 | 行内提示 +「仍可开始」 | 否 |
| `ok` | 全部通过 | 无提示或显示规范化后的地址 | 否 |

**`socks5` vs `socks5h` 必须解释**，否则用户永远不知道为什么"加了 h 就好了"：

> `socks5://` 在**本机**解析 DNS，可能被污染或泄露；`socks5h://` 让**代理端**解析。判断 DNS 污染相关结论时，这个差异会直接改变结果。建议默认用 `socks5h://`。

交互：以「建议」形态出现（非错误），附一键切换协议前缀，保留其余部分。

### 7.3 凭据打码

| 阶段 | 呈现 |
| --- | --- |
| 输入中 | 密码段 `•` 逐字符；提供「显示」切换（`aria-pressed`），默认隐藏 |
| 失焦后 | 重绘为 `user:••••••@host:port`，**DOM 不保留明文**（`04-security.md`：凭据只在内存） |
| 折叠摘要（running） | `socks5h://user:••••@127.0.0.1:7890` |
| 复制地址 | 自动脱敏 + Toast「已复制（凭据已移除）」 |
| 导出报告 | 必走唯一脱敏函数；字段白名单（TB-3） |
| `RawJsonViewer` / 日志 | 同样脱敏；含凭据的原始字段前端直接不渲染 |

补充：「显示密码」不跨会话不持久化；password 段单独处理 `autocomplete`；始终提供「清空凭据」，清空只清凭据不动 host/port。

### 7.4 直连对照：不是第四种模式，是一次额外发车

**决定**：对照是 `baselineCompare: boolean` 开关，不是模式。理由：用户目标是"两种都测"，若要求他先测、再切直连、再测、再心算差值，就是三步骤的产品缺陷。

开关下方常驻一行：
> 开启后先测当前配置，再自动测一次直连，两轮串行（避免互相抢带宽）。耗时约翻倍，流量预算约翻倍（62 MB → 约 124 MB）。

ComparePanel（仅双轮都有结果时出现）：

```
                开代理        直连        Δ        方向
吞吐           58.2 Mbps    0.4 Mbps   +57.8     ↑ 更好
TTFB            210 ms       1,820 ms   -1,610    ↑ 更好
成功率          5/5          1/5        +80%      ↑ 更好
ChatGPT         被人机验证拦截  未连通      —         ↑ 更好
Gemini          正常          未连通      —         ↑ 更好
API 端点        可用·无密钥     未连通      —         ↑ 更好

┌──────────────────────────────────────────────────────────────┐
│ 判断：代理确实起作用了。                                       │
│ 但 ChatGPT 仍被人机验证拦截 —— 换节点可解，不是代理坏了。       │
└──────────────────────────────────────────────────────────────┘
```

规则：
- 每行显式标注"↑ 更好"方向（不同指标好坏方向可能相反，避免误读）；
- 直连侧结论**不得**出现"你的代理有问题"（PRD US-10.2）；
- Δ≈0 时结论提示「两者表现一致，代理可能未生效，或本就通畅」，并引导核对出网方式徽章；
- 对照轮期间第一轮结果常驻可见，只在顶部加细进度条，**不出现第二个 ProbeGrid**。

```
│    · 判定依据：content-length 匹配，响应未截断             │
│    · 命中特征：无                                        │
│    · 采样：5/5 成功                                      │
│                                                          │
│ ⑥ 原始数据 RawJsonViewer（默认折叠，已脱敏，可复制）       │
│                                                          │
│ ⑦ [ 重测此项  1 ]   [ 复制此项结论 ]                      │
└──────────────────────────────────────────────────────────┘
```

约束：
- ② 对所有探测项都显示——阶段瀑布本身就在回答"卡在哪一层"，是 P3/P4/P5 最有价值的诊断信息。
- ③ 对纯可达类替换为**采样时间线**（每次采样一个成功/失败块）。
- ⑥ **默认折叠**：它是给技术支持型用户（R3）与客服的，不是普通用户的第一视角。
- ⑤ 必须回答"凭什么下这个结论"，而非再抄一遍指标；展示判定规则 ID（如 `cf_challenge_v2`）。
- 「复制此项结论」输出 3–5 行纯文本（供粘贴工单），不是 JSON。

### 8.3 详情内的重测语义

- 重测后详情保持展开，数据**原位替换**（不清空再填，避免闪烁）；
- 顶部出现「这是 14:32:07 的重测结果」时间戳；
- 结论变好/变差时，① 旁显示 Δ 徽章「较上次 ↑ / ↓」。

**部分重测后的总分口径 = 甲案（upsert），已定稿**

```
scoreInput = merge(上一次 run 的 6 项结果) ← upsert(本次重测项)
total      = 基于 scoreInput 重新归一化计算
```

| 规则 | 要求 |
| --- | --- |
| 组合方式 | 基于**最近一次各项结果**组合计算，新值覆盖旧值（upsert），未重测项沿用旧值 |
| 生成时间 | 总分旁显示 `组合于 14:32`，详情里每项各显示自己的采集时间——两者的时间差必须可见，不能伪装成同一次采集 |
| 徽章 | 总分带「组合结果」标注（不是"未完成"，二者语义不同：`partial` 是缺项，这是新老混排） |
| 混合配置 | 若重测前改过配置，旧项结果永久带「旧配置结果」灰底标注（§3.4 #5），且总分标注「混合配置，仅供参照」 |
| 禁止 | ✗ 把未重测项视为过期而清零；✗ 只显示"本次重测那一项"而隐藏总分；✗ 静默重算而不给时间戳 |

> 选甲案而非"视为新 run 冻结旧结果"，是因为用户点「重测 P3」的意图是**修正这一项**，不是丢弃整份报告。若走乙案，用户为看一个 401 的更新要付 6 项流量，与 US-05.3 直接冲突。

## 9. 键盘可达性与屏幕阅读器

### 9.1 全局快捷键

| 键 | 作用 | 生效范围 | 备注 |
| --- | --- | --- | --- |
| `Enter` | 开始检测 | 焦点不在输入框/按钮内；`idle`/`configuring`/`done`/`partial` | `running` 下为 no-op（防误触清空） |
| `Enter` | 重测全部 | `done`/`partial` 且焦点不在某卡上 | 与上行同键，按状态分流 |
| `Esc` | 取消检测 | `running` | 最高优先级，即使焦点在输入框内也生效 |
| `Esc` | 关闭最上层浮层 | 有 Sheet/Drawer/Overlay | 优先级高于取消 |
| `1`–`6` | 重测第 1–6 项 | 非 `running`，且该项已 settled | 该项未 settled 或已有重测在飞 → 忽略 + Toast 说明原因 |
| `e` | 导出 | 有结果时 | 打开 ExportSheet |
| `d` | 跳到第一张"受限/不可用"的卡并展开 | 有结果时 | 把用户直接送到最需要看的地方 |
| `t` | 切换主题 | 全局 | — |
| `?` | 快捷键帮助 | 全局 | Overlay，Esc 关闭 |

规则：
- 在 `input` / `textarea` / `[contenteditable]` 内一律不拦截（`Esc` 除外）；
- 每个快捷键都有可见等价按钮，不做"仅键盘可达"的隐藏功能；
- 不注册与系统/浏览器冲突的组合（`⌘W`/`Ctrl+W` 等）；
- macOS 显 `⌘`、Windows 显 `Ctrl`，主按钮上的提示符号随之切换。

### 9.2 Tab 顺序

```
HeaderBar : 品牌 → 出网徽章（可聚焦看详情）→ 历史 → 主题 → 帮助
ConfigBar : 模式1 → 模式2 → 模式3 → 地址输入 → [显示密码] → [清空]
            → 档位 → 对照开关 → 高级选项 → 「开始检测」
ProbeGrid : 自左而右、自上而下 卡1…卡6
            卡内：主体（展开/收起）→ 重测按钮
Detail    : 结论 → 图表(figure 可聚焦) → 证据 → JSON 折叠 → 动作
FooterBar : 导出 → 关于
```

约束：
- `running` 折叠配置区时，被折叠内容必须 `hidden`/`inert`，不能仍被 Tab 到；
- 骨架屏期间不产生可聚焦元素；
- 卡片重测完成后**焦点不跳走**，只更新状态文字；
- 展开详情后焦点移到详情标题，关闭后回到触发卡片；
- 不使用正 `tabindex`；图标按钮必须有 `aria-label`。

### 9.3 屏幕阅读器要点

| 场景 | 实现 |
| --- | --- |
| 单项完成 | 单一 `aria-live="polite"` 区域播报「P1 Google 大文件下载完成，偏慢，12.4 Mbps」；**只在状态变化时播报，进度不播** |
| 全局完成 | 「检测完成，6 项中 5 项正常。整体结论：可以顺畅用 AI。」 |
| 取消 | 「已取消，保留 4 项结果。」 |
| 进度 | `role="progressbar"` + `aria-valuetext="已测 4.2 秒，共 8 秒"`；不定态不设 `aria-valuenow`，只给 `aria-valuetext="预计约 8 秒"` |
| 三态徽章 | 图标形态 + 文字 + `aria-label` 三重；禁止只靠颜色（见 §6.6） |
| 图表 | `role="img"` + `aria-label` 概述（「速度曲线：起始 42 Mbps，中段衰减至 8 Mbps，末段回升」），并提供可聚焦的「以文本方式查看数据」 |
| 阶段瀑布 | 用 `<dl>`（阶段名 → 耗时），非纯 div |
| 不可用控件 | `aria-disabled="true"` 而非 `disabled`，保留可聚焦性以朗读原因 |
| 页面标题 | 状态变化时更新 `<title>`：「检测中 4/6 · ProxyLens」→「完成 · 可以顺畅用 AI · ProxyLens」 |
| 减少动效 | 尊重 `prefers-reduced-motion`，条纹与展开降级为瞬时 |

## 10. 组件树

### 10.1 约定

- **每个组件一个文件**，默认导出，文件名 = 组件名（PascalCase）。
- 组件只有三种角色：**展示**（无副作用）、**容器**（订阅 store 并下发）、**原语**（无业务语义）。
- 判定一律下沉到纯函数（`verdict.ts` / `validateProxy.ts` / `maskProxy.ts` / `format.ts`）；**组件内禁止出现阈值判断与文案拼接**。
- 数据向下、事件向上；共享可变状态只经 store。
- 组件不认识"第几项"，只认识 `probe` 对象与 `probeId`——新增探测项无需改组件。
- 框架无关：props/events 用通用 TS 风格描述，React / Preact / Svelte 可直译。

## 11. 响应式

### 11.1 首要约束：V1–V4 必须挤进 1440×900 首屏

这是硬约束，**优先于任何栅格美观考虑**（§1.4）。因此：

- `done` / `partial` 状态下 ConfigBar 必须折叠为一行摘要（不折叠则必然溢出）；
- ScoreStrip 与 VerdictCard 在视觉上属于同一屏组，不允许被拆到两屏；
- ProbeGrid 的第一行（3 张卡）应与 V1–V4 同时可见或仅需极短滚动。

### 11.2 各宽度下的布局变化

| 宽度 | ConfigBar | ProbeGrid | Verdict | 详情形态 | 其他 |
| --- | --- | --- | --- | --- | --- |
| **≥1920** | 单行铺满，地址框与档位并排 | **3 列**，卡间距放大，容器有最大宽度约束（避免横向拉伸变形） | 左栏固定 + 右侧 ProbeGrid 双栏布局（结论常驻可视） | 内联展开 | Footer 显示完整环境信息 |
| **1440–1919** | 单行 | **3 列** | 顶部整宽 | 内联展开 | 基准布局，所有设计以此刻度校准 |
| **1280–1439** | 单行，高级选项收进折叠 | **3 列**（卡内次指标减为 1 个） | 顶部整宽 | 内联展开 | 详情展开占满一行 |
| **1024–1279** | 两行（模式 + 地址换行） | **2 列** | 顶部整宽 | 内联展开 | 微曲线可隐藏（保留主指标） |
| **<1024**（最小窗口） | 三行纵向堆叠 | **1 列** | 顶部整宽，动作列表折叠为「查看 3 条建议」 | **全屏 Sheet** | Footer 精简为一行；Compare 表改为逐项纵向对照 |

**最小窗口尺寸：960×640。** 低于此尺寸不做流式重排，而是显示提示层：
> 「窗口过小。请将窗口放大到至少 960×640，或最大化。」

理由：本工具的信息密度下限是"6 项状态 + 结论 + 一个数字"，强行压进更小视口只会产出不可读的界面。给出明确下限比给一个不可用的移动布局更诚实。

### 11.3 降级顺序（空间不足时按此顺序砍）

1. 微曲线（`ProbeSparkline`）
2. 次指标（保留 ≤1 个）
3. Team/环境细节（FooterBar 折叠）
4. 卡内阶段 stepper 的标签文字（保留图形）
5. Compare 表的"方向"列（并入结论句）

**永不砍**：V1 结论、V2 三态、V4 出网方式、取消按钮、单项重测入口、主指标数字。

### 11.4 最小窗口以下（<960×640）的降级是"拒绝"，不是"重排"

提示层只给两个动作：「最大化窗口」与「继续以紧凑模式查看（功能受限）」。紧凑模式**允许**砍掉详情与导出，**不允许**砍掉 V1 与 V2——即使窗口只有 640 宽，裁决与三态仍是可读的。

### 11.5 三态可区分性验收（零成本、不依赖色觉假设）

三个动作，任一不通过则三态方案判失败，必须改形态而不是改颜色：

| 动作 | 做法 | 通过标准 |
| --- | --- | --- |
| **1. 灰度化** | 对三态截图去色（灰度 / `filter: grayscale(1)`） | 仍能不看文字就分出三类 |
| **2. 缩小** | 截图缩到 12px 图形尺寸 | 受限态的缺口、不可用态的斜杠不糊成同一个「脏点」 |
| **3. 挖掉颜色与位置** | 遮住阶段条位置信息，只留图形 + 文案首字 | 三态仍可辨（验证 §6.6 通道分层：判断层不依赖位置通道） |

> 这三条是**验收动作**，不是设计理念。任何"我觉得已经能区分了"的自评不算通过；必须留三张图在 PR 里。ui-designer 已据此裁定「缺口圆环 90° 缺口 / 12px 下限」，本条用于回归保护。

## 12. 边界与容错体验

| 场景 | 用户看到什么 | 交互 |
| --- | --- | --- |
| **断网**（本机） | 应用态 `failed`；C 区：「本机当前没有可用网络」+ 归因「系统环境」+ 动作「恢复网络后重试」；**文案不提代理、不提 AI**（PRD #750） | 隐藏无意义的重测按钮；导出仍可用（本地生成，PRD US-06.6） |
| **代理配置错** | ≥5 项同层同阶段失败 → 折叠为单条根因 + 「去修改代理」+ 排除法「切直连测一次」 | 不甩 6 张红卡；改配置即回 `configuring` |
| **429 限流** | `被限流` 徽章（受限态）+「出口 IP 短期请求过多，等 1–2 分钟或换 IP，不是配置问题」 | 卡片提供「稍后重测」；不自动重试 |
| **证书错误** | `证书异常` + 「可能是系统时间偏差或代理在解密流量」 | **不提供"忽略证书继续"按钮**；仅在证据区给出 issuer/有效期（详情层，不进首屏） |
| **长时间无响应** | 单项先超时（`TIMEOUT`），全局不阻塞；C 区提示「有 2 项超时，其余结果仍有效」 | 超时时长由档位决定；超时项可单独重测 |
| **SSE 中断** | 顶部非阻塞 Banner「连接中断，正在重连（2/3）」，结果灰化只读 | 重连成功续跑；3 次失败转 `failed` 并保留 `partial` 视图 |
| **引擎崩溃** | `failed` + 「检测引擎未响应」+「重试」+「查看日志」 | 已渲染结果不丢 |
| **本地存储写满**（历史快照） | Toast「历史快照已达上限，最旧一条已被替换」 | 明确告知淘汰（PRD US-09.6），不静默丢 |
| **系统睡眠/唤醒** | 唤醒后若在 `running`，说明「检测在休眠期间中断」并转 `partial` | 不自动续跑（数据已断，续跑无意义） |
| **代理地址含凭据且导出** | 报告中为 `user:***@host:port` | 导出前预览脱敏结果 |

## 13. 给下游的输入约束

### 13.1 给 ui-designer（`08-ui-spec.md`）

1. **三态必须三通道**：可用 / 受限 / 不可用，颜色最多占 1 个通道（§6.6）。受限态要有"半填充/缺口"这类非红非绿的形态。
2. **首屏 V1–V4 的排版是本设计的骨架**：V1 结论、V2 三态、V3 速度语义、V4 出网方式必须在 1440×900 一屏内。不要把 ConfigBar 做成展开态占据首屏。
3. 卡片正面只有 1 个主数字；不要引入表格。
4. 状态码 / TTFB / p90 / CV / TLS 版本 / 证书 issuer **不得出现在首屏**（§1.4 禁用词）。
5. 阶段瀑布与速度曲线需要"文本替代"视图，设计时预留其排版。
6. 折叠态 ConfigSummary 需设计成一行可读摘要，这是首屏腾空间的关键。
7. 每条红灯都要预留一个动作位（§6.7），且**归因位要能容纳五类责任方**（用户/代理/目标服务/系统环境/网络运营商），不能按三类排版。
8. 降级标记（§5.4）需要常驻但低干扰的视觉位。
9. **档位 A–E（优/良/可用/较差/不可用）是 PRD 强制可见项**（§6.8）：需设计「分数 + 档位词」的组合呈现，且总分与三个分项分各有一处。注意档位词与三态词字面重叠（都有"可用/不可用"），必须用不同的视觉位区分——档位挂在分数旁，三态挂在卡片徽章上。
10. 「样本不足，暂不评级」（N<3）需要独立形态，不能复用 E 档的视觉（§6.8-4）。

### 13.2 给前端实现

1. **两条正交轴**：`lifecycle` 与 `verdict` 分开存（§3.2）。禁止合并成一个枚举。
2. **每个 probe 独立切片 + 定向 patch**；禁止整页重渲（§4.1）。
3. 三层节流：采样 4Hz / 图表 rAF≤10Hz / 数字 2Hz（§4.2）。取消后 ≤500ms 停刷。
4. `runId` + `epoch`：取消即递增，丢弃旧事件（§3.4-#7）。
5. **判定全在 `verdict.ts`（纯函数，可单测）**；组件只取文案。新增文案只改 `verdictCopy` / `statusCopy`。
6. `StartButton` 永不 disabled；校验失败在点击时拦截并聚焦（§7.2）。
7. 脱敏唯一收口 `maskProxy.ts`；导出与复制都必须过它。
8. 单一 `aria-live` 区域；只在状态变化播报；数字变化不播（§9.3）。
9. `ProbeProgress` 四变体，按探测项类型选择，不能用统一进度条（§4.3）。
10. 组件不认识"第几项"，为未来增删探测项留出扩展点。

### 13.3 需要与 `06-engine-design.md` 对齐的接口点

- Verdict 枚举的最终取值与每个取值的**判定依据字段**（用于证据区展示）；
- 阶段名列表（DNS / TCP / TLS / TTFB / Body…）与阶段耗时结构；
- 采样推送事件的字段名与频率；
- **`NET_FAIL` 的 `subReason` 枚举**（`dns_pollution` / `tcp_refused` / `tls_cert` / `ipv6_only` / `timeout_connect` 等）——这是五类归因（§6.7）能否落地的前提，没有 `subReason` 前端就只能写"网络失败"；
- **分项分 → A–E 档位的映射**（PRD §3.2 给了区间，但 `06` 需确认每个分项都用同一套区间，还是 AI 可用性另设）；
- 阈值（决定 `PASS` 与 `SLOW` 的边界）——**本文不定义数值**；
- 每档位的 `expectedProbeCount`（决定"轻量档不会永远 partial"）。

### 13.4 与 `05-prd.md` 的对齐状态

1. **已对齐**（PRD v1.0 定稿后复核，明细见附录 C）：探测项 9 态、结论类型 C1–C7、A–E 五档、五类归因、运行模式四枚举（`SYSTEM` / `CUSTOM` / `DIRECT` / `HISTORY`）、按钮不 disabled、取消后两动作、截图摘要版面。
2. **本文对 PRD 的两处补充**（PRD 未写、但交互必须定）：`cancelled` 作为瞬态过渡态而非稳定状态；`lifecycle` 与 `verdict` 双轴拆分。二者不改变任何 PRD 用户可见行为。
3. **仍待 `06` 回填**：`NET_FAIL.subReason` 枚举、分项分→A–E 的映射是否统一、各档位 `expectedProbeCount`。这三项缺失会导致 §6.7 归因与 §3.3 完整度判定无法落地。

## 附录 C · 与 PRD v1.0 的对齐补充（PRD 定稿后修订）

PRD 全文落盘后复核，以下 9 项为**新增或修正**，凡与前文冲突，以本附录为准。

### C-1 探测项状态：只用 PRD §3.1 的 9 态（已改 §0.2 / §3.2）

`PASS / PASS_WITH_NOTE / SLOW / BLOCKED_BY_POLICY / CHALLENGED / RATE_LIMITED / TIMEOUT / NET_FAIL / SKIPPED`。
**不新增枚举**：`TLS_ERROR` 归入 `NET_FAIL`（`subReason = tls_cert`）；`UNSTABLE` 废除，改为结论层 C6。
UI 上禁止出现「失败 / 错误 / 无法连接」这类不带归因的状态名（PRD §3.1 强制规则 1）。

### C-2 结果档位必须可见（新增）

PRD §3.2 定义 5 档：`A 优(85–100) / B 良(70–84) / C 可用(55–69) / D 较差(30–54) / E 不可用(0–29)`。
`ScoreStrip` 的每个分项与总分都**必须同时显示分数与档位词**（如「网络质量 72 · 良」），且导出报告同样可见。只给数字不给档位词 = 违反 PRD。

### C-3 取消后的两个动作（修正 §2.2 / §2.3）

取消**不是终点**。用户看到「已停止（3/6 项完成）」后，必须提供两个显式动作：

```
┌─────────────────────────────────────────────────────────┐
│ 已停止（3/6 项完成）                                     │
│ [ 继续剩余 3 项 ]        [ 重新开始 ]        [ 导出当前结果 ] │
└─────────────────────────────────────────────────────────┘
```

- 「继续剩余项」= 只对 `SKIPPED(cancelled)` 的项发起新 run，已 settled 的项**保留原值不回退**；
- 「重新开始」= 清空全部重跑；
- 二者都不得改变已得结果的可用性（PRD US-05.2：中断结果仍可导出，且标注「第 N 项未完成」）。

### C-4 直连模式必须持续可见（修正 §7.1）

直连提示**不能是一次性 toast**，必须常驻：
① `HeaderBar` 出网徽章显示「直连」（六值枚举之一）；
② `ConfigBar` 折叠摘要首词为「直连」；
③ 结论区顶部一条窄色带标「直连模式 · 结果不代表代理表现」。
三处同时存在，直到用户切回其他模式（PRD US-10.1 要求"不会误以为仍在代理下"）。

### C-5 改配置后必须阻断式提示（修正 §3.4-#5）

原方案（弱化提示条 + 保留旧结果）**不满足 PRD**。改为**阻断式**：

```
┌──────────────────────────────────────────────────────────┐
│ ⚠ 配置已修改，当前结果是旧配置下产生的                       │
│    旧：socks5h://127.0.0.1:7890                           │
│    新：socks5h://127.0.0.1:7891                           │
│    [ 立即重新检测 ]   [ 仅查看旧结果 ]   [ 取消修改 ]        │
└──────────────────────────────────────────────────────────┘
```

- 出现时机：改配置后**立即**弹出（modal 或同等强度的阻断层），不是角落提示条；
- 选择「仅查看旧结果」后，旧结果区永久带一条灰底标注「旧配置结果」，且**导出文件名/报告头标注配置已变更**；
- 选择「立即重新检测」→ 直接进 `running`。

### C-6 截图友好摘要（新增独立界面）

PRD FR-E5。/ 「导出 → 摘要」与 `Ctrl/Cmd+P` 共用同一版面。

- 目标尺寸：**1280×800 一屏不滚动**；在 **125% 系统缩放下同样成立**（意味着实际内容宽度按 ~1024 设计）；
- 关键信息**不依赖任何交互即可见**：结论（C1–C7 之一）、三分项分 + 档位词、出网方式、6 项状态（9 态徽章，含 `SKIPPED`）、关键指标（吞吐/TTFB/成功率）、生成时间 + `schemaVersion`；
- 隐藏：配置输入控件、重测按钮、Footer 细节、历史入口；
- 强制浅色（打印友好），三态用形状 + 文字（灰度可辨）；
- 导出 JSON 时同时提供 `incomplete` 标记与 `configChanged` 标记。

### C-7 历史对比视图的模式差异警示（新增）

PRD FR-F2。历史对比与 §7.4 的"开代理 vs 直连"**不是同一个东西**：前者比两次不同时间的运行，后者比同一时刻的两条路径。

对比视图必须包含：Δ总分、Δ三分项（各带档位词）、逐项状态变化；
- **状态降级项高亮**（如 `PASS` → `BLOCKED_BY_POLICY`）；
- 两条记录**模式不同或代理地址不同**时，顶部必须警示：「两次运行的配置不同（{模式A} vs {模式B}），差值仅供参考」——不得让用户误以为是线路变好/变差。

### C-8 C3 的视觉权重（修正 §6.3）

PRD 把 **C3「能连，但用不了 AI」** 定为**核心输出、产品唯一护城河**。因此：
- C3 结论卡片的视觉重量必须**高于** C5/C6/C7；
- C3 必须包含归因句「本次问题不在速率」，且"能连不能用"四字要能在首屏扫读到；
- C3 下的 `NextActionList` 必须是 PRD 给定的三条（换出口地区 / 等 1–5 分钟 / **不要反复重连节点**），第三条是关键反直觉建议，不可省略。

### C-9 禁止项复核（确认不做）

- ✗ 任何"忽略证书校验 / 跳过安全验证"的开关或一键按钮（PRD 第 6 章 #5）；
- ✗ 节点列表、订阅解析、批量节点测试入口（越界成测速器）；
- ✗ 自动修复 / 自动切换节点 / 自动改系统代理（PRD §1.4：只诊断不处置）；
- ✗ 把 `CHALLENGED` 与 `BLOCKED_BY_POLICY` 合并展示；
- ✗ 把 `SKIPPED` 当 0 分或用通过色；
- ✗ 首屏出现状态码裸数字 / TTFB / p50 / p90 / CV / TLS 版本 / 证书 issuer。
