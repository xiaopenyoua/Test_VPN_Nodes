## 1. 产品定位

### 1.1 一句话定位

> **ProxyLens 是一套「系统代理整体能力体检」工具**：用真实业务行为（打开 AI 服务网页、下载大型 CDN 资源、起播视频分片）测量**网络速度、稳定性、AI 可用性**，回答一个具体问题——
> **"我现在这套代理，能不能顺畅用 AI？卡不卡、稳不稳、会不会被墙/被风控？"**

它不是节点测速器，不是带宽测试仪，不是 VPN 客户端。

### 1.2 它必须回答的三个问题

| # | 用户问题 | 对应产品能力 | 关键产出 |
|---|---|---|---|
| Q1 | **能用吗？** 我是被墙、被风控、还是地区限制？ | AI 可用性语义判定（差异化核心） | 每个 AI 目标的状态枚举 + 一句人话结论 |
| Q2 | **有多快？** 打开 ChatGPT / 看 YouTube 卡不卡？ | 吞吐与首字节测量（真实资源下载） | 吞吐 Mbps（p50/p90）、TTFB、起播耗时 |
| Q3 | **稳不稳？** 是一时快还是持续能用？ | 多次采样成功率、抖动、衰减形态 | 成功率、抖动、连续失败次数、衰减形态 |

三个问题**同等重要**，缺任一个都不算完成体检。brief §2.2 明确要求"必须区分「慢」与「不可用」"——这是本产品的立身之本。

#### 1.2.1 护城河的真实构成（v1.2 修订，采纳 `01` §4.3 的修正）

原本我把护城河表述为"AI 语义判定"。**这个判断偏薄**：语义判定（挑战页 / 地区页识别）本质是一个特征库，一周可被抄；而且现有竞品的"ChatGPT 可用性检测"网页测的是**检测站自己的服务器**，不是用户本机这条代理——是**路径错位**，修起来不难。

因此本产品的护城河必须表述为**三层叠加**，缺一层都可被复制：

| 层 | 内容 | 可复制性 |
|---|---|---|
| L1 业务语义 | 真实业务事务 + 十态语义判定（挑战/策略/限流/劫持分开） | 低门槛，可被抄 |
| L2 **分责归因** | `blame` 五值（`LOCAL`/`PROXY`/`TARGET`/`SECURITY`/`UNKNOWN`），把失败落到"谁的问题" | 中，需要探测项设计与判定逻辑配套 |
| L3 **两个参照系** | ① **空间对照**：直连 vs 代理（FR-A3）② **时间对照**：同线路历史快照（FR-F） | 高门槛，需要产品结构支撑，抄不走单点功能 |

> 结论：**"能连但不能用 AI"只是入口，真正的差异是"能说清是谁的问题，并且有两个参照系可证"**。任何后续功能取舍，应以"是否强化 L2/L3"为准绳，而不是继续堆探测项。

### 1.3 与「节点测速器」的差别（防走偏对照表）

| 维度 | 节点测速器（**不是**本产品） | ProxyLens（本产品） |
|---|---|---|
| 测量对象 | 单个节点 / 单条订阅条目 | **当前整套系统出网能力**（TUN 全局接管 / 系统代理 / 直连） |
| 测量手段 | ICMP ping、TCP 握手 RTT、小包下载 | **真实业务事务**：AI 网页可达性、大文件流式下载、视频分片 range 请求 |
| 输入 | 订阅链接、节点列表 | 代理地址（**可留空**） |
| 输出 | 一堆节点延迟排名，让用户自己挑 | **一次结论**：能/不能、快/慢、稳/不稳 + 证据 + 建议 |
| 是否判断"能不能用 AI" | 不判断 | **核心判断**：403/429/451/人机验证/地区限制/响应截断 |
| 是否区分"慢"与"不可用" | 通常只有数值 | 强制区分（状态枚举 + 分项分） |

> 工程上可借鉴历史 `clash-speedtest` 的结构，但**产品思路必须完全独立**（brief §4 已明确）。

### 1.4 明确不做（Out of Scope）

严格对齐 brief §3，逐条给出理由，防止被"顺手加一下"侵蚀：

| 不做的事 | 理由 |
|---|---|
| 节点管理、订阅解析、Clash 规则编辑 | 属 clash-verge 等客户端的产品域。做了会造成定位混淆，且用户已有此类工具，重复投入无收益 |
| IP 落地库 / 流媒体解锁（Netflix、Disney+）完整判定 | 依赖大体积 IP 库与频繁更新的解锁指纹，维护成本远超价值；结论易失效反伤可信度。**仅允许**轻量地区推断（见 FR-P3/P4）并标注"推断，不作结论" |
| 服务端、云账号体系、数据同步、遥测上报 | 用户所测为敏感网络环境，引入隐私与合规负担及运维成本；离线本地工具即可满足需求 |
| 自动化定时压测集群 / 无人值守长期监控 | 需常驻服务与历史数据库，属"监控系统"而非"体检工具"。历史对比是**本地快照**（FR-F），不是长期监控 |
| 移动端（iOS / Android） | brief §3 明确首版不做；移动端系统代理语义与桌面完全不同，需独立设计 |
| 自动修复 / 自动切换节点 / 自动改代理配置 | 越界成为代理客户端，且有"改坏用户网络"风险。工具只诊断，不处置 |
| 承诺"绝对不会被风控 / 账号安全" | 无法为上游服务风控策略背书，承诺即失信（见第 7 章文案禁令） |
| **上传测速** | **v1.1 补充**：上传确为真实痛点（跨境传素材），但 brief §2.1 六项探测中无上传项。首版不做，**但必须在 UI 与报告中显式声明"本工具不测上传"**，避免用户误以为已覆盖（`01-product-research.md` §6.4 同结论） |

### 1.5 易混淆边界（提前钉死，防止误实现）

| 模糊说法 | 本产品的确定含义 |
|---|---|
| "代理地址留空 = 直连" | **错**。留空 = **走操作系统默认出网路径**（可能被 TUN 接管、可能走系统代理、也可能是真直连）。UI 必须展示**实际识别到的出网方式**，不得假设 |
| "测速" | 指真实资源**流式下载**得到的吞吐，不是带宽上限，不是 ping |
| "AI 可用" | 指该服务端点在当前出网路径下**能返回正常业务响应**；不等于"登录后功能全可用"，也不等于"账号未被风控" |
| "支持 SOCKS5" | 必须包含 `socks5h://`（**远程 DNS**）语义差异：DNS 在代理端还是本地解析，会直接改变 DNS 污染判定，UI 需可区分 |
| "并发测试" | 并发发生在**不同探测项之间**；同一探测项内部的吞吐测量必须在受控条件下进行，否则数字无意义（受控条件交 `06` 定义） |

## 2. 用户角色与核心用户故事

### 2.1 角色定义

| ID | 角色 | 特征 | 核心诉求 | brief 依据 |
|---|---|---|---|---|
| R1 | **代理重度用户**（主角色） | 长期订阅机场或自建，TUN / 系统代理 7×24 常开；会遇到"昨天还好今天不行" | 一句话告诉我现在能不能用、哪儿出问题 | §1 用户原话要点 |
| R2 | **AI 开发者 / 研究者** | 依赖 `api.openai.com` 做开发，脚本跑一半超时会直接阻塞工作 | API 端点可达性 + 稳定性，能否长连接 | §2.1 P5、§2.2 稳定性层 |
| R3 | **技术支持型用户** | 常被问"我为什么上不了 ChatGPT"；需要可转发、可复现的证据 | 导出报告发给对方，或让对方自己跑一次 | §2.5 可导出报告 |
| R4 | **网络质量记录者**（次要） | 换机场 / 换线路 / 换时段前后想对比 | 历史快照与差值对比 | §2.2 综合评分、本文 FR-F |
| R5 | **轻度用户**（v1.2 补充，与 R1 并列重要） | 代理是"别人帮我配好的"，自己不知道端口/协议/TUN 是什么 | **只要一句人话裁决 + 可复制的证据**；任何技术名词都会劝退 | `01` §1 C 类；`01` §5.3 |

> **R5 为何与 R1 并列**：R5 决定了"一句话人话 + 可复制证据"这个**不可让渡的形态**，而该形态最容易被工程视角牺牲成"更好的 curl"。若只以 R1 为准，产品会滑向命令行工具的图形壳。故 §3.1.2 首屏三态、7.4 禁令 #11（首屏禁技术指标）都是为 R5 设的硬约束，**不得因"专业用户想看数字"而放宽**。

> **用户声音（v1.2 补入，带来源标注，禁止去掉标注当事实引用）**
> > 「延迟 30 毫秒绿油油的，网页就是打不开 —— 到底是我有问题还是它有问题？」（*composite，基于痛点机理推演，**非访谈原文** `[I]`*）
>
> 这是把 `01` 的 T1「假连接」与"归因诉求"合成的典型语句：数字漂亮 + 视觉确认（绿点）+ 实际不可用。它同时解释了为什么本产品必须做 **AI 语义判定** 与 **责任层归因**——只报数字的工具在这里是**谎报**。
> 另：`01-product-research.md` §8.1 已声明未做一手访谈，本文所有用户侧描述同样为 `[I]` 级推断，**下游不得当作"已证实需求"引用**；凡未经 `01` §9.3 验证闭环的假设，只能写成"假设 + 验证方式"，不得写成验收标准。

### 2.2 用户故事（每条含可测验收标准）

编号 `US-xx`，括号内为关联功能 ID 与优先级。

**US-01｜零配置开局（P0 · FR-A1 / FR-A4 / FR-C1）**

> 作为 **R1 代理重度用户**，我想 **打开工具什么都不填就直接点"开始检测"**，以便 **不用搞清楚代理跑在哪个端口，也能得到一次完整体检**。

**验收标准**
1. 首次启动后，主界面在**无任何输入**的情况下，"开始检测"按钮**处于可点击状态**（非禁用）。
2. 点击后自动进入"系统代理"模式，并在 **1s 内**展示识别到的出网方式，取值限定于枚举：`系统代理（HTTP）` / `系统代理（SOCKS）` / `TUN 或全局接管` / `环境变量代理` / `直连` / `无法识别`（不允许自由文本）。
3. 若识别结果与预期不符，用户能在同一屏**不离开当前页面**切换为"直连"或"自定义代理"后重跑。
4. 全程**不需要用户输入**端口号、PAC 地址或订阅链接。

---

**US-02｜区分"被墙"与"被风控"（P0 · FR-P3 / FR-P4 / FR-E2）**

> 作为 **R1**，我想 **知道 ChatGPT 打不开到底是网络不通、被地区限制、还是撞上人机验证**，以便 **决定换节点、等一会儿再试、还是去处理账号问题，而不是盲目重连**。

**验收标准**
1. 对 `chatgpt.com` 的检测结果**必须**落在 §3.1 状态枚举内，不允许输出"失败"这类无信息量结论。
2. 以下三种情形必须产出**互不相同**的状态与文案（可用 mock 响应复现）：
   - `403` 且响应体命中 Cloudflare 挑战特征 → `CHALLENGED`
   - `451` 或响应体命中 "not available in your country" 类特征 → `BLOCKED_BY_POLICY`
   - DNS / 连接阶段失败 → `NET_FAIL`
3. 结论区必须可**下钻看证据**：至少包含 HTTP 状态码、命中的特征类型、判定依据字段（不要求展示完整响应体）。
4. 同一场景重复执行 3 次，状态判定**结果一致**（不允许同输入抖动出不同状态）。

---

**US-03｜看清"慢"而不是只看到数字（P0 · FR-P1 / FR-D1 / FR-E1）**

> 作为 **R1**，我想 **在下载过程中就看到速度曲线与当前值，而不是盯着转圈等 30 秒**，以便 **中途判断这个代理已没救、直接取消**。

**验收标准**
1. 下载类探测项开始后 **≤ 1s** 出现首个实时数值（当前速率）。
2. 实时数值刷新间隔 **≤ 500ms**，刷新过程**不阻塞交互**（滚动、切 Tab、点取消均即时响应，无白屏卡顿）。
3. 结束时展示**平均吞吐、p50、p90、TTFB** 四项，缺一不可。
4. 吞吐在过程中衰减时，结论必须体现"是否衰减"这一事实（呈现形态由 `06`/`08` 定）。

---

**US-04｜一次轻量检测要够快（P0 · FR-C5 / NFR-4）**

> 作为 **R1**，我想 **在 10 秒内得到"能用 / 不能用"的快速判断**，以便 **在切节点前后快速验证，不打断工作节奏**。

**验收标准**
1. 选"轻量"档后，从点击到全部探测项结束（或超时收口）**总时长 ≤ 10s**（参考机、网络正常前提下，10 次执行至少 9 次达标）。
2. 轻量档结束仍**必须**给出三个分项（速度 / 稳定性 / AI 可用性）与总分，不得因省时而缺结论。
3. 某项在轻量档被跳过时，UI 必须显式标注"本次未测"，不得用 0 分或通过色冒充。

---

**US-05｜随时取消、随时重测（P0 · FR-C2 / FR-C3）**

> 作为 **R1**，我想 **在发现速度明显不对时立刻取消，只重测出问题的那一项**，以便 **不为一个问题再等一遍完整流程**。

**验收标准**
1. 检测中"取消"按钮**始终可见可点**；点击后 **≤ 500ms** 进入"已取消"状态，UI 停止刷新指标。
2. 取消后已产生的部分结果**不丢弃**：已完成项结果仍可见、可导出，导出内容明确标注"本次为中断运行，第 N 项未完成"。
3. 结果列表中每个探测项均提供独立重测入口；单项重测**只重跑该项**，其他项结果保持原值、不闪回"检测中"。
4. 单项重测完成后总分与结论**自动重算**，并标注"基于最近一次各项结果组合"。

---

**US-06｜把报告发给别人（P0：JSON / P1：Markdown · FR-E3 / FR-E4）**

> 作为 **R3 技术支持型用户**，我想 **导出一份带证据的报告发给同事**，以便 **不远程控制对方电脑，也能让他看懂问题在哪**。

**验收标准**
1. 导出格式至少两种：**JSON** 与 **Markdown**，入口在结果页 ≤ 2 次点击可直达。
2. Markdown 报告**人类可读**：含运行时间、出网方式、三个分项分、六项探测状态、关键指标表、结论与建议；在纯文本查看器中不依赖额外渲染即可读懂。
3. JSON 报告**机器可读**：字段稳定、可被脚本解析；含 schema 版本号与生成时间。
4. 报告**不含任何代理凭据**（用户名 / 密码 / URL 认证段），导出前必须脱敏。
5. 导出成功后明确告知落盘路径，并可直接打开所在目录。
6. 断网状态下**导出仍可用**（本地生成）。

---

**US-07｜API 场景的稳定性判断（P0 · FR-P5 / FR-P6）**

> 作为 **R2 AI 开发者**，我想 **确认 API 端点不只是"能 ping 通"，而是能稳定完成多次请求**，以便 **判断脚本会不会跑一半挂掉**。

**验收标准**
1. 对 API 端点的无凭据请求，返回 `401` 时必须判定为**服务可达**（`PASS` 或 `PASS_WITH_NOTE`），文案明确"未提供密钥，401 属正常可达"。**不得**判为失败。
2. 稳定性维度必须基于 **≥ 3 次**采样（默认 5 次，可配 3–20），输出：成功次数 / 总次数、失败率、抖动值、最长连续失败次数。
3. 存在连续失败时，结论区必须提示"存在连续 N 次失败，可能不适合长连接任务"。
4. 抖动与成功率必须与"单次最快值"**分开呈现**，禁止用最优值代表整体稳定性。

---

**US-08｜知道自己在花多少流量（P0 · FR-G3 / FR-D2）**

> 作为 **R1**，我想 **在开始前就知道这次检测大概耗多少流量**，以便 **在手机热点或计费流量下决定是否跑深度检测**。

**验收标准**
1. 开始之前即展示预估流量预算（按当前档位与字节预算计算，含"约"字，1 位小数，单位 MB）。
2. 检测中展示已消耗流量累计值；结束时展示实际消耗总量。
3. 实际消耗**不得超过**预估值的 120%（超出视为缺陷）。
4. 默认档位下总流量预算 **≤ 100MB**。

---

**US-09｜知道"这次比上次好了还是差了"（P1 · FR-F）**

> 作为 **R4 网络质量记录者**，我想 **把本次结果与上周同一条线路并排比较**，以便 **判断是机场真的变差，还是我自己感觉错了**。

**验收标准**
1. 每次完成的检测自动保存为本地快照（无需手动"保存"）。
2. 历史列表展示至少：时间、出网方式、总分、三个分项分；支持任选两条对比。
3. 对比视图展示**差值**（Δ总分、Δ各分项、各探测项状态变化），并标注"变好 / 变差 / 持平"。
4. 状态发生降级（如 `PASS` → `BLOCKED_BY_POLICY`）必须在对比视图中**高亮**。
5. 至少保留最近 **50 条**快照；支持删除单条或清空全部。
6. 触达上限时按时间淘汰最旧记录，且该行为在 UI 有说明（不得静默丢数据）。

---

**US-10｜轮换服务商时做对照实验（P0 · FR-A3 / FR-E1）**

> 作为 **R1**，我想 **对同一次检测分别跑"开代理"和"直连"并看到差值**，以便 **确认到底是代理的问题还是本来就这样**。

**验收标准**
1. 存在显式"直连（绕过系统代理）"模式；选择后界面明确标示当前为直连，**且用户不会误以为仍在代理下**（视觉 + 文字双重提示）。
2. 直连模式下目标不可达时，结论不得出现"你的代理有问题"这类误导（因为未走代理），应改为"直连不可达，属预期"。
3. 用户可在**不重建整个流程**的前提下切换模式并重跑（切换成本 ≤ 2 次点击）。
4. 报告必须记录本次运行所用模式；两种模式的差值对比由 FR-F 承担（P1）。

## 3. 产品级枚举（下游必须复用，不得各自发明）

### 3.1 探测项状态枚举（10 态 · v1.1 定稿）

每个探测项在同一时刻**只能处于一个状态**。此枚举是 `06`（判定逻辑）、`07`（状态机与配色映射）、`09`（用例断言）的共同词表。
**线上契约值（wire value）= 本表左列**；下游内部可保留自有命名，但越过事件边界（`probe_result.status`）与进入 UI / 报告前**必须**映射为本表值。

| 状态 | 中文展示名 | 含义 | 计分处理 |
|---|---|---|---|
| `PASS` | 可用 | 达成该探测项成功条件，指标在"良"及以上 | 正常计分 |
| `PASS_WITH_NOTE` | 可用（有说明） | 业务可用但有需告知的附注（API 返回 401、需登录页说明"网络已通"、地区推断为非偏好区） | 正常计分，附注展示 |
| `SLOW` | 可用但慢 | 事务完成但指标落在"差"档（TTFB 超阈 / 吞吐低 / 起播超阈） | 计分但扣分，**不得**判为不可用 |
| `BLOCKED_BY_POLICY` | 被策略拦截 | 命中地区限制 / 451 / 明确封禁页特征 | 该项计 0，计入 AI 可用性红结论 |
| `CHALLENGED` | 人机验证拦截 | 命中 Cloudflare / Akamai 挑战页或验证码容器特征 | 该项计 0，文案必须与"被墙"区分 |
| `HIJACKED` | 疑似劫持 | 发生伪造 200 / 证书替换 / Host 跳变 / 响应体被替换截断（第 6 章 #5、#15） | 该项计 0，**且触发全局红警 + 总分封顶**（见 §3.1.3） |
| `RATE_LIMITED` | 被限流 | 返回 429 或命中限流页特征 | **该项不计 0 分**：从 AI 可用性分项中**整体排除**（既不进分子也不进分母），报告标注"因限流未参与评分"。文案"稍后重试"，**不**归因代理质量。**（v1.2 修订）**原方案"计 0 分"存在自相矛盾：既然不归因代理，就不该让用户"什么都没做错"却掉档（`07` 复核指出） |
| `TIMEOUT` | 超时 | 在配置超时内未完成 | 该项计 0，计入稳定性失败 |
| `NET_FAIL` | 网络失败 | DNS / TCP / TLS 阶段失败（不含证书被替换，后者归 `HIJACKED`） | 该项计 0，归因网络层 |
| `SKIPPED` | 未测 | 用户取消、档位跳过、前置条件不满足 | **不计分**，按已测项归一化，必须显式标注 |

**强制规则**
1. 禁止出现"失败 / 错误 / 无法连接"这类不带归因的状态名。
2. `SLOW` 与 `TIMEOUT` / `NET_FAIL` **必须**在 UI 上明确区分（前者"能但慢"，后者"不能用"）。
3. `SKIPPED` 项**不得**当作 0 分参与总分，否则会被误导为"全部失败"。
4. `RATE_LIMITED` 与 `SLOW` **不得合流**：限流不是慢，处置方式不同（等待 vs 换线）。
5. `HIJACKED` 不得降级为 `NET_FAIL` 处理：前者是安全性事件，必须让用户看见。
6. **"不计分族"必须统一口径**：`RATE_LIMITED` 与 `SKIPPED` 都**不得拉低** AI 可用性分项，但两者语义不同（前者"测到了、服务在限流"，后者"没测成"），UI 必须分别标注，不得混成一个"未知"。
7. **归一化分母 = 实际参与评分的项数**。任何不计分项必须从分母剔除，并在分项旁标注"N/6 项计入"——这条同时约束 `06` 的算法与 `07` 的呈现（`06` 若已按"全项为分母"实现，需修正）。

#### 3.1.1 与 `06-engine-design.md` 内部命名的映射（**v1.1 新增，消解冲突**）

`06` 采用了一套内部 verdict 命名。为免大规模返工，**允许 `06` 内部保留原名**，但 `probe_result.status` 必须按下表输出本表值。`06` 需新增 `RATE_LIMITED` / `TIMEOUT` / `SKIPPED` 三个输出值（其现设计把 429 并入 `DEGRADED`，**必须拆开**）。

| 本表（wire value） | `06` 内部名 | 备注 |
|---|---|---|
| `PASS` | `AVAILABLE` | 含 `AVAILABLE` 且 P2 `media_path="unavailable"` 的情形 → 应输出 `PASS_WITH_NOTE` 而非 `PASS`（页面通但媒体链路未验证，属附注） |
| `PASS_WITH_NOTE` | `AUTH_REQUIRED` | P5 的 401 已映射为 `AVAILABLE`，保持 |
| `SLOW` | `DEGRADED` | **仅**限"慢/降级"语义 |
| `BLOCKED_BY_POLICY` | `REGION_BLOCKED` | — |
| `CHALLENGED` | `CHALLENGE` | 统一为 `CHALLENGED` |
| `HIJACKED` | `HIJACKED` | 本表 v1.1 已新增，语义一致 |
| `RATE_LIMITED` | **需新增**（现为 `DEGRADED`） | 429 + `rate_limit_exceeded` / `insufficient_quota` / 纯 429 均归此 |
| `TIMEOUT` | **需新增** | `06` 现以 `soft_fail` / 超时码表达，需在边界显式输出 |
| `NET_FAIL` | `UNREACHABLE` | — |
| `SKIPPED` | **需新增** | 取消 / 档位跳过 / 前置不满足 |

#### 3.1.2 首屏三态聚合（决不允许二元）

**首屏 Headline 只允许三值**：`可用` / `受限` / `不可用`。此要求来自 `01-product-research.md` §5.3 V2（"禁止二元"）与 `08-ui-spec.md` 已实现的结论短语；十态是**详情层**词表，不得直接铺在首屏。

| 三态 | 由十态聚合 | 判据 |
|---|---|---|
| **可用** | 全部 ∈ {`PASS`,`PASS_WITH_NOTE`,`SLOW`} | 无任何拦截/劫持/限流 |
| **受限** | 至少一项 ∈ {`CHALLENGED`,`BLOCKED_BY_POLICY`,`RATE_LIMITED`}，但无 `HIJACKED` | "能到达但被拦" —— 这是本产品最强的差异化表达 |
| **不可用** | 至少一项 ∈ {`NET_FAIL`,`TIMEOUT`,`HIJACKED`} 且无任何"可用"项 | 完全不通，或疑似劫持 |

> 硬规则：**只要出现一项 `CHALLENGED` 或 `BLOCKED_BY_POLICY`，首屏就不得显示"可用"**（这是竞品最大的坑，见 `01` §2.1）。

> **硬规则 2（v1.2 新增，可测量）**：**首屏"裸数字"≤ 4 个**（裸数字 = 不带档位词、不带业务语义的纯数值）。超过即视为"退回体温计"，判定为不合格。这是为 R5 轻度用户设的量化闸门，`09` 需写为负向断言。
>
> **硬规则 3（v1.2 新增）**：**二元判定残留 = 0**。任一 AI 探测项若只输出"可用 / 不可用"两值，即为不合格（必须落在十态之一，首屏聚合必须是三态）。

#### 3.1.3 责任层归因（`blame` · v1.1 新增）

每个探测项除 `status` 外必须输出一个 `blame` 值，用于回答"这是谁的问题"。此维度是 `01-product-research.md` §6.1 M9 的 P0 要求，也是"可分责"定位的硬支撑。

| `blame` | 含义 | 典型状态 | 用户该做什么 |
|---|---|---|---|
| `LOCAL` | 本机 / 系统环境（无网络、系统时间错、IPv6-only、PAC 不可判定） | `NET_FAIL` + 环境异常 | 先修环境 |
| `PROXY` | 代理链路（代理拒绝连接、认证失败、TUN 未生效） | `NET_FAIL` / `SKIPPED` | 检查代理软件与模式 |
| `TARGET` | 目标服务自身（5xx、限流、地区策略、人机验证） | `RATE_LIMITED` / `BLOCKED_BY_POLICY` / `CHALLENGED` | 等待或换出口地区 |
| `SECURITY` | 疑似中间人（证书替换、伪造 200、内容截断） | `HIJACKED` | 立即停用该链路 |
| `UNKNOWN` | 无法归因（证据不足） | 任意 + 置信度低 | 重测或换模式对照 |

> 硬规则：`blame = TARGET` 的失败**不得**拉低"代理质量"相关展示权重（第 7 章 C3/C4 已按此构词）；`blame = UNKNOWN` 必须同时输出置信度标注，禁止伪装确定。

### 3.2 结果档位（5 级，用于分项分与文案）

| 档位 | 区间（分项分 0–100） | 展示词 | 语义 |
|---|---|---|---|
| A | 85–100 | 优 | 可作主力线路使用 |
| B | 70–84 | 良 | 日常可用，偶有等待 |
| C | 55–69 | 可用 | 能用但体验打折 |
| D | 30–54 | 较差 | 勉强可用，建议换线路 |
| E | 0–29 | 不可用 | 无法完成目标业务 |

> **PRD 只约束**：档位数量、区间边界、展示词必须与上表一致且**在 UI 与导出报告中显式可见**。各指标如何映射到 0–100 分、权重如何分配、如何归一化，由 `06-engine-design.md` 定稿（brief §2.2 要求"禁止黑箱"）。若 `06` 需调整区间边界，必须回传 PM 更新本文。

### 3.3 运行模式枚举

| 模式 | 枚举值 | 说明 |
|---|---|---|
| 系统代理（默认，零配置） | `SYSTEM` | 走操作系统默认出网路径，不假设是否 TUN / 系统代理 / 直连 |
| 自定义代理 | `CUSTOM` | 用户填写代理地址，协议支持见 FR-A2 |
| 直连对照 | `DIRECT` | 显式绕过系统代理 |
| 历史快照（只读） | `HISTORY` | 查看历史记录时使用，不可再运行 |

> **（v1.2 澄清，`07` 复核提出）此"运行模式"与 FR-A4 的"出网方式"是两套不同枚举，不得混用**：
> - 运行模式 = **用户选了哪种配置策略**（`SYSTEM`/`CUSTOM`/`DIRECT`），由用户决定；
> - 出网方式 = **系统实测把流量从哪送出去**（`系统代理（HTTP）`/`系统代理（SOCKS）`/`TUN 或全局接管`/`环境变量代理`/`直连`/`无法识别`），由探测得出。
> 二者可以不一致：用户选 `SYSTEM`（未配代理），实测出网走 TUN——这是**正常且必须正确展示**的组合。测试时**禁止**把"选了 SYSTEM"当成"实际走了 TUN"。

### 4.A 代理模式与出网识别

#### FR-A1｜系统代理模式（留空即用）— **P0**

- **输入**：用户在代理配置区**留空**（或显式选择"系统代理"）；无其他必填项。
- **输出**：本次运行以 `SYSTEM` 模式执行；UI 显示识别到的出网方式（§2.1 US-01 的 6 值枚举）+ 识别依据摘要（一行，如"检测到 TUN 虚拟网卡接管默认路由"）。
- **验收标准**
  1. 代理地址为空时，**不得**报"请输入代理地址"这类阻断性错误。
  2. 识别在 **1s 内**完成；识别失败时状态为 `无法识别`，但**仍允许继续检测**（用"走系统默认路径"语义执行），不得直接阻断。
  3. 识别结果必须可复现：同一环境连续 5 次识别，结果一致。
  4. UI 上必须能区分"系统代理"与"直连"，二者**不得**共用同一文案。

#### FR-A2｜自定义代理 — **P0**

- **输入**：一条代理地址字符串。必须支持协议：`http://`、`https://`、`socks5://`、`socks5h://`；支持 `user:pass@` 认证段；支持 IPv4 / IPv6 字面量与域名、省略端口时按协议默认端口。
- **输出**：解析后的代理配置摘要（协议、主机、端口、是否带认证、DNS 解析位置）+ 校验结果。
- **验收标准**
  1. 合法输入在 **≤ 300ms** 内返回校验通过，并展示归一化后的地址摘要。
  2. 非法输入必须给出**具体原因**（枚举见第 6 章 #2），不得只显示"地址无效"。
  3. `socks5://` 与 `socks5h://` 必须在 UI 上**可区分**（远程 DNS 与否），并各自给出提示：后者"由代理端解析域名，可规避本地 DNS 污染"。
  4. 认证段在 UI 默认**掩码显示**（如 `user:••••`），提供"临时显示"控制，**不提供**"永久显示"。
  5. 修改代理地址后，已完成的旧结果必须被标记"基于旧配置"，不得静默混用（详见 FR-C4 一致性规则）。

#### FR-A3｜直连对照模式 — **P0**

- **输入**：用户选择"直连（绕过系统代理）"。
- **输出**：本次运行以 `DIRECT` 模式执行，网络上不经过任何代理。
- **验收标准**
  1. 该模式下必须有**持续可见**的"直连中"标识（非仅一次性 toast）。
  2. 直连模式下若全部探测项失败，结论文案为"直连状态下目标不可达，属预期；请切换回代理模式对比"（见第 7 章文案规则 T-DIRECT-FAIL）。
  3. 模式切换（代理 ↔ 直连）≤ 2 次点击，且无需重启应用。
  4. 报告与历史快照必须记录 `mode` 字段，取值属 §3.3 枚举。

#### FR-A4｜出网方式识别与展示 — **P0**

- **输入**：当前系统网络配置（无需用户输入）。
- **输出**：出网方式枚举 + 识别依据一行摘要 + 是否受 TUN 接管的布尔标志。
- **验收标准**
  1. 必须覆盖 brief §4 描述的真实环境：TUN 全局接管开启、但系统 HTTP/SOCKS 代理未单独开启、且环境变量存在代理的情形。此种情形下不得显示为"直连"，应显示 `TUN 或全局接管` 或 `环境变量代理`（二者择一，取更具体的，且在摘要中说明另一者同时存在）。
  2. 若系统代理与环境变量**同时存在且不一致**，必须提示冲突（第 6 章 #14）。
  3. 出网方式必须在结果报告与历史快照中持久记录。

#### FR-A5｜代理可用性预检 — **P0**

- **输入**：解析后的代理配置（`CUSTOM` 模式）。
- **输出**：预检结论 —— 代理端口是否可连接。
- **验收标准**
  1. 自定义代理模式下，点击开始后**先做预检**，预检耗时 ≤ 2s。
  2. 预检失败时**立即中止**并给出针对性文案（拒绝连接 / 认证失败 / 超时），**不进入**六项探测，避免用户白等。
  3. 系统代理模式下**不做**此预检（因为没有显式代理端点），直接进入探测。
  4. 预检失败必须仍可导出"失败报告"（含失败原因），便于 R3 转发。

#### FR-A6｜凭据安全（产品级约束）— **P0**

- **输入**：含认证段的代理地址。
- **输出**：凭据仅存在于本次运行内存；落盘与导出内容一律脱敏。
- **验收标准**
  1. 配置文件、缓存、历史快照、导出报告（JSON / Markdown）中**均不得**出现明文密码。测试方法：写入含密码的地址 → 跑一次检测 → 全量搜索本地数据文件，不得命中该密码字符串。
  2. **（v1.1 修订）代理地址整体不做持久化**：重启后代理输入框为**空**，用户需重新填写。理由：`04-security.md` 的 S-11 验收要求"数据目录中零命中且相关目录不存在"，若持久化主机/用户名仍会留下可定位的网络环境痕迹；且"记住代理"会诱导用户长期忽略"我到底在用哪条线路"。非敏感设置（主题 / 语言 / 阈值 / 窗口尺寸）不受此限，可持久化，但**禁止**包含任何代理字段。
  3. 崩溃 / 异常退出后，日志与临时文件中不得残留密码。
  4. 安全实现的威胁建模与具体防护由 `04-security.md` 定稿；本节只约束**可验证的产品结果**。

### 4.B 探测项（真实业务行为，非连通性）

> 六项探测对应 brief §2.1 的 P1–P6，编号保持一致以便追溯。目标端点以 brief 为准；若某端点在某平台或时段不可用，允许替换**同厂商同语义**的等价端点，但必须在报告中记录实际使用的端点。

#### FR-P1｜Google 大文件下载（吞吐主测）— **P0**

- **输入**：字节预算（默认 20 MiB，可配，见 FR-G3）、单请求超时（见 FR-G4）、采样窗口。
- **输出**：**平均吞吐 Mbps、p50、p90、TTFB、连接建立耗时、抖动、衰减形态（上升 / 平稳 / 衰减 / 剧烈波动）**、实际下载字节数、使用的端点。
- **验收标准**
  1. 必须完成**流式**下载（边下边算），不得等全部字节落盘后再算速率。
  2. 七项输出指标**全部**必须出现在结果页与 JSON 报告中；衰减形态为枚举值，不允许缺失。
  3. 实际下载字节数**不得超过**配置预算的 105%（防超量扣流量）。
  4. 与对照点（brief 提到的 `speed.cloudflare.com`）的用途必须明确：仅作**对照组**，其数值不得与 Google CDN 数值混算成一个吞吐分（避免跨厂商混淆）。
  5. 下载途中被限速到极低（< 0.5 Mbps 持续 ≥ 5s）时，必须判定为 `SLOW` 并**主动提前收口**，不得死等到超时才给结果（见第 6 章 #11）。
  6. 结束后必须给出"用户可感知"的一句话（如"下载 20MB 用了 8.4s，相当于 19 Mbps，看 1080p 视频够用"），该句式由第 7 章文案规则约束。

#### FR-P2｜YouTube 播放链路 — **P0**

- **输入**：目标为 `youtube.com` → `googlevideo.com` 播放清单，采用 range 请求下载分片；分片数与字节预算可配。
- **输出**：**起播耗时（time-to-first-segment）、分片平均速率、卡顿次数、降速标志、可用性状态**、命中链路阶段（清单获取 / 分片下载）。
- **验收标准**
  1. 必须真实请求播放清单并据其取分片，**不得**用静态硬编码分片地址（否则无法反映真实链路）。
  2. 五个输出指标必须齐全；"起播耗时"与"分片平均速率"必须**分开**呈现，不可合并成一个"YouTube 速度"。
  3. 若清单可获取但分片全部失败，状态必须为 `NET_FAIL` 或 `SLOW`（视失败性质），且文案明确指出"清单可达、分片不可达"这一关键信息（这是典型的中转被阻断特征）。
  4. 若 `youtube.com` 可访问但 `googlevideo.com` 不可达，必须**单独标记**该子阶段失败，不得整体判"YouTube 不可用"而不给归因。
  5. 不得对视频做实际解码 / 播放，只做分片传输测量（产品边界：这是体检，不是播放器）。
6. **（v1.1 新增）三级降级必须可见，不得静默降级**：若播放清单直链不可得（`06` D1 已实测 `youtubei` 三种 client 均失败），允许依次降级为「共享域可达 + 媒体域可达分离判定」→「仅共享域判定」；每次降级必须在该项结果上标注**降级层级 + 置信度**，并写入报告。降级时状态最高只能给 `PASS_WITH_NOTE`，不得给 `PASS`，且总分受封顶（`06` CAP-7 已定义 `Total ≤ 75`）。

#### FR-P3｜ChatGPT 网页可达性 — **P0**

- **输入**：`https://chatgpt.com/` 主文档 + `cdn.oaistatic.com` 静态资源抽检（至少 1 个资源）。
- **输出**：HTTP 状态、TTFB、状态枚举（§3.1）、命中特征类型、页面关键指纹结论（标题 / 关键 DOM 是否存在）、静态资源可达性。
- **验收标准**
  1. **必须**能区分以下四种结果并给出不同状态（可用 mock 复现）：
     - 正常页面 → `PASS`
     - Cloudflare 挑战页 → `CHALLENGED`
     - 地区限制 / 封禁页（含 451）→ `BLOCKED_BY_POLICY`
     - DNS / TCP / TLS 失败 → `NET_FAIL`
  2. 静态资源（`cdn.oaistatic.com`）必须单独输出可达性。若主文档可达但静态资源不可达，必须提示"页面可能白屏或加载不全"——这是用户真实痛点的关键分支。
  3. 页面关键指纹判定必须基于**至少两项**独立特征（如标题 + 关键 DOM 节点），不得仅凭状态码下结论（防劫持返回 200 假页面）。
  4. 地区推断只允许作为**附注**（`PASS_WITH_NOTE`），措辞必须为"推测"，禁止输出"你在 X 国"这类断言。
  5. 不得提交任何登录凭据、不得尝试登录、不得写入任何用户账号相关状态（产品边界）。

#### FR-P4｜Gemini 网页可达性 — **P0**

- **输入**：`https://gemini.google.com/`。
- **输出**：与 FR-P3 **同构**的输出（HTTP 状态、TTFB、状态枚举、特征类型、指纹结论），额外增加"地区不可用页"识别结论。
- **验收标准**
  1. 输出字段集合与 FR-P3 保持一致（同一套渲染与同一套报告结构），不得另造字段。
  2. "not available in your country" 类地区限制必须识别为 `BLOCKED_BY_POLICY`，且文案必须区别于"被防火墙阻断"（前者是服务方拒绝，后者是链路不通）。
  3. Gemini 常见的情形——**能打开页面但对话功能不可用**——必须能通过指纹特征反映出来，至少给出"页面可达，功能页特征缺失"这一档结论（`PASS_WITH_NOTE` 或 `SLOW`，由 `06` 依据特征命中率定）。
  4. 与 P3 相同：禁止登录、禁止账号操作。

#### FR-P5｜OpenAI API 端点 — **P0**

- **输入**：`https://api.openai.com/v1/models`，**不带**任何密钥。
- **输出**：可达性结论、TLS 握手耗时、TLS 版本、响应码语义解释、稳定性采样结果（复用 FR-P6 的采样机制）。
- **验收标准**
  1. 返回 `401` 必须判为 `PASS_WITH_NOTE`，文案为"未提供密钥，401 表示网络已通达 OpenAI 服务，属正常结果"。
  2. 返回 `200`（异常情形）必须按**双重条件**判为可疑、不得直接判 `PASS`（v1.2 采纳 `04` S-34）：① 状态 200；**且** ② 响应体无法解析出 OpenAI 标准错误信封（`{"error":{"type":"invalid_request_error"...}}`）或 `content-type` 非 `application/json` → 判 `HIJACKED`（或 `NET_FAIL`），文案"响应异常，可能被中间层拦截"。无密钥请求 OpenAI 必返 401，200 是极强的劫持信号。
  3. 返回 `403` / `429` / `451` / `5xx` 分别映射到 `BLOCKED_BY_POLICY` / `RATE_LIMITED` / `BLOCKED_BY_POLICY` / `NET_FAIL`（5xx 归因待 `06` 确认，PRD 要求"必须给出归因，不得归为成功"）。
  4. TLS 版本必须展示（如 TLS 1.3）；若握手失败或证书异常，必须有明确文案指向"证书 / 中间人"方向（第 6 章 #6）。
  5. 该探测项**绝不**向用户索取 API Key，也**不**支持填写 Key（首版不做的取舍：避免凭据保管责任，见 §4.X）。

#### FR-P6｜通用国际链路基线 — **P0**

- **输入**：`https://www.google.com/generate_204`、`https://www.gstatic.com/generate_204`；采样次数 N（默认 5，可配 3–20）。
- **输出**：**RTT（p50 / p90）、丢包或失败率、抖动（jitter）、连续失败次数、每端点分别的成功率**。
- **验收标准**
  1. 必须按配置次数完成采样，且**每端点分别**给出成功率（不得合并成一个数）。
  2. 必须输出抖动值，且抖动与 RTT 分开呈现（抖动的具体算法由 `06` 定，PRD 要求"必须显示且口径在文档中可见"）。
  3. 必须输出"最长连续失败次数"，用于回答"会不会用着用着断"。
  4. 两个端点结果**不一致**时（一个通一个不通），必须显式提示分歧，并在结论中说明"链路部分可用"（这是 GFW 常见特征，不能平均成一个"半通"结论糊弄过去）。
  5. 该项是**基线**：其失败不必然导致 AI 项失败，两者结论必须能独立成立（防止"基线通了就断定 AI 可用"的错误推断）。

### 4.C 执行控制

#### FR-C1｜一键全量检测 — **P0**

- **输入**：运行模式（默认 `SYSTEM`）+ 档位（轻量 / 深度，默认轻量）。
- **输出**：六项探测的编排执行，逐项产出状态与指标，最终产出总分与结论。
- **验收标准**
  1. 一次点击即开始，无需二次确认（除非当前有正在运行的检测，此时二次确认"覆盖当前结果"）。
  2. 六项**全部**出现在结果列表中，未测项显式标 `SKIPPED`，不得凭空省略。
  3. 全量检测中任一项失败**不得**中止其他项（失败隔离）。
  4. 全量检测结束时，总分、三个分项分、结论、建议全部产出；缺任一项视为未完成。
  5. 重复点击"开始"不得并发启动两次运行（必须去重 / 排队）。

#### FR-C2｜单项重测 — **P0**

- **输入**：用户点击某一探测项的"重测"。
- **输出**：仅该项重新执行，其余项结果不变；总分与结论重算。
- **验收标准**
  1. 重测期间其他项**不显示**"检测中"，其数值不被清零。
  2. 重测结果的时间戳独立记录；报告中该项标注"该项为单独重测，时间 HH:mm:ss"。
  3. 重测不得受全局"取消"以外的状态阻塞；单项重测期间"取消"只作用于该项（文案要说明作用范围）。
  4. 重测 3 次同一项，状态判定一致（若不一致，说明该探测器判定不稳定，属缺陷）。

#### FR-C3｜全局取消 — **P0**

- **输入**：运行中点"取消 / 停止"。
- **输出**：所有进行中的探测立即停止；已得结果保留。
- **验收标准**
  1. 取消响应 **≤ 500ms**（从点击到 UI 显示"已停止"）。
  2. 取消后**不得**有残留网络请求继续消耗流量（测试方法：取消后观察流量计数在 2s 内停止增长）。
  3. 取消后 UI 状态必须清晰："已停止（3/6 项完成）"，并提供"继续剩余项"与"重新开始"两个明确选择。
  4. 取消后仍可导出部分结果（US-05 第 2 条）。
  5. 应用关闭 / 退出时若有运行中任务，必须先完成取消清理，不得留下后台进程（见 FR-H1 第 2 条）。
6. **（v1.2 裁决，"继续剩余项"的计分口径 —— `07` 提出甲/乙两案，此处定为"甲 + 守卫"）**
   - **默认方案甲**：继续后只跑原 `SKIPPED` 项，已 settled 项**不回退**，跑完按全部已测项重算总分，并标注"基于最近一次各项结果组合"（与 US-05.4 一致，本质是批量版单项重测）。
   - **守卫条件（满足任一即自动降级为方案乙）**：① 从停止到继续的间隔 **> 10 分钟**；② 期间**网络环境发生变化**（切换 Wi-Fi / 插拔网线 / 代理模式或地址被修改 / 系统休眠唤醒）。降级为乙时：旧结果**冻结为独立快照**，继续的部分作为**新 run**，**两段不得混算总分**，`partial` 态下总分呈现为"分两段"。
   - 所有情形必须在报告中记录 `resume_gap_seconds` 与 `resumed` 标记，供 `09` 与 `06` 复算。
   - **对 `06` 的连带要求**：归一化分母必须能区分"一次连续 run 的已测项"与"跨 run 拼接的已测项"，不得默认全并。

#### FR-C4｜结果一致性（防混用）— **P0**

- **输入**：先后使用不同模式 / 不同代理 / 不同设置运行。
- **输出**：结果集的"配置指纹"标识；跨配置结果不得静默混算。
- **验收标准**
  1. 每次运行的报告必须记录：模式、代理摘要（脱敏）、档位、关键设置（并发数 / 字节预算 / 超时 / 采样次数）、时间戳。
  2. 若用户修改了模式或代理后**仅在部分项上重测**，UI 必须提示"当前结果来自不同配置，总分不可比"，并给出"全部重跑"入口。
  3. 该提示为**阻断式提示**（需用户确认继续），不得仅用弱化文字带过。

#### FR-C5｜检测档位（轻量 / 深度）— **P0**

- **输入**：用户选择档位，默认"轻量"。
- **输出**：两套预设参数组合（影响采样次数、字节预算、超时时长），并展示该档位的预估耗时与预估流量。
- **验收标准**
  1. 轻量档：总时长 ≤ 10s；深度档：默认 ≤ 60s，可配至 300s。
  2. 切换档位时，预估耗时与预估流量**立即更新**（≤ 200ms）。
  3. 两档的差异必须在 UI 上有**可读的一行说明**（如"轻量：快速判断能不能用；深度：连续采样，看稳定性与衰减"）。
  4. 轻量档下 P6 采样次数不得低于 3 次（否则抖动无意义）；深度档默认 5 次以上。

### 4.D 实时指标流

#### FR-D1｜流式指标刷新 — **P0**

- **输入**：检测过程中的实时事件（每完成一次采样 / 每收到一段字节）。
- **输出**：界面实时展示当前速率、已传输量、已耗时、当前阶段。
- **验收标准**
  1. 首个数值 **≤ 1s** 出现；刷新间隔 **≤ 500ms**。
  2. 刷新期间主界面保持可交互：滚动、切换 Tab、点击取消**无卡顿**（主观判定标准：不出现"转圈且按钮无响应" > 300ms 的现象）。
  3. 检测完成后**停止**刷新，不得有幽灵定时器继续刷新（空闲 CPU 见 NFR-2）。
  4. 实时数据必须与最终统计**自洽**：最终平均吞吐不能与过程中展示的数值量级明显矛盾（误差 > 20% 视为缺陷）。

#### FR-D2｜进度与流量可见 — **P0**

- **输入**：编排进度与已消耗字节。
- **输出**：已完成 / 总数、当前项名称、累计流量。
- **验收标准**
  1. 进度必须展示"已完成 N / 总 M"的量化值，不得只有进度条动画。
  2. 累计流量在检测中可见，结束时给出总量（US-08）。
  3. 剩余时间估算必须基于实际进度，且**允许不显示**（宁可没有，也不要给出明显错误的估算——错误估算会损伤信任）。

#### FR-D3｜阶段状态可见 — **P0**

- **输入**：单个探测项内部的阶段进展（如 DNS → 建连 → TLS → TTFB → 传输）。
- **输出**：当前所处阶段的可读名称。
- **验收标准**
  1. 至少能看出该项"卡在哪个阶段"（这是区分 DNS 污染 / 建连被断 / TLS 被劫持的关键 UX）。
  2. 该项失败时，最后停留的阶段必须保留展示，不得清空。
  3. 阶段名用中文人话，不使用纯技术缩写堆叠（如用"域名解析"而非"DNS"；TLS 可保留但需配中文说明）。

### 4.E 结果报告与导出

#### FR-E1｜总分与分项分 — **P0**

- **输入**：各探测项的指标与状态。
- **输出**：**总分（0–100）+ 三个分项分（速度 / 稳定性 / AI 可用性，各 0–100）+ 每项对应的档位词**（§3.2）。
- **验收标准**
  1. 分项分**必须**是三分，缺一不可；brief §2.2 明确要求"分项分 + 总分"。
  2. 评分必须**可解释**：UI 与报告中必须能看到"各分项由哪些探测项的哪些指标构成"，且权重表对用户可见（`06` 提供具体权重数值）。
  3. 分数为整数（四舍五入），不使用小数以免营造虚假精度。
  4. **稳定性要求**：同一环境连续两次全量检测，各分项分差 **≤ ±10**；超过则视为噪声过大，需由 `06` 调整算法。
  5. `SKIPPED` 项不计入分项分，分项分按已测项归一化，并在 UI 标注"基于 N/M 项"。
6. **（v1.2 新增）`RATE_LIMITED` 同样不计分、不进分母**（见 §3.1 强制规则 6–7），且该类运行必须在历史对比中标为"本次含限流项，不建议与常规运行直接比较"。
7. **（v1.2 新增）误报率硬指标**：把"可用"误判为"不可用"比漏判更致命。要求**误报率（false-negative，即可用被判不可用）≤ 5%**，以 20 次已知可用环境的重复检测为样本，判定口径由 `09` 固化。"宁可说受限，不可说失联"是本产品的判定基调（`01` §7.3 同结论）。
  6. 禁止只有一个总分而无分项（无法满足 brief "区分慢与不可用"）。

#### FR-E2｜结论与建议 — **P0**

- **输入**：分项分 + 各探测项状态。
- **输出**：**一句结论 + 最多 3 条建议**，按第 7 章文案规则生成。
- **验收标准**
  1. 结论必须唯一（不接受"综合来看有好有坏"这类无判断力的输出）。
  2. 至少能产出第 7 章定义的 **5 类结论**之一，且每类都能通过指定条件触发（可由 mock 复现）。
  3. 建议不超过 3 条，每条必须**可执行**（含具体动作，如"切换为直连重跑以确认是代理问题"），不得出现"建议优化网络"这类空话。
  4. 结论必须能下钻到证据（US-02 第 3 条），且证据与结论**不得矛盾**（测试方法：逐项比对结论关键词与对应探测项状态）。
  5. "能连但不能用 AI"这一结论必须**单独成一类**（这是本产品的核心价值输出，不允许被"部分可用"吞掉）。

#### FR-E3｜导出 JSON — **P0**

- **输入**：一次运行（完整或中断）的结果集。
- **输出**：一个 JSON 文件，落盘到用户可见位置。
- **验收标准**
  1. 必含字段：schema 版本、应用版本、生成时间、运行模式、代理摘要（脱敏）、档位与设置、三项分项分、总分、六项探测的 `{状态, 指标, 证据摘要, 耗时}`、结论、建议。
  2. 字段命名稳定（同一版本内不得变动）；新增字段必须向后兼容（只增不改语义）。
  3. 文件可被标准 JSON 解析器无错解析；UTF-8 编码，中文不转义为乱码。
  4. 不含凭据（FR-A6 第 1 条）。
  5. 文件名含时间戳，避免覆盖；连续导出 3 次产出 3 个文件。
  6. 导出失败（如目录无写权限）必须给出可操作提示，不得静默失败。

#### FR-E4｜导出 Markdown — **P1**

- **输入**：同 FR-E3。
- **输出**：一份人类可读的 Markdown 报告。
- **验收标准**
  1. 结构固定：标题（含时间与模式）→ 结论 → 分项分表 → 六项探测明细表 → 建议 → 附注（设置与端点）。
  2. 纯文本可读：无 HTML 依赖；表格列数 ≤ 6，避免过宽不可读。
  3. 必须包含"如何解读本报告"的 2–3 行说明，使其可被非技术用户（R3 的同事）看懂。
  4. 中断运行的报告必须带显式"⚠ 本次未完成"标记与完成项计数。
  5. 与 JSON 报告**同源**：同一运行导出的两种格式，关键数值必须完全一致（不得各自计算）。

#### FR-E5｜截图友好摘要 — **P1**

- **输入**：一次运行结果。
- **输出**：一屏内可完整截图的结论区（含总分、三分项、六项状态、一句结论）。
- **验收标准**
  1. 在默认窗口尺寸与 1280×800 最小尺寸下，摘要区**不需要滚动**即可完整进入一屏。
  2. 摘要区不包含需要交互才可见的关键信息（否则截图后信息丢失）。
  3. 该区域不依赖动效完成呈现（截图时不得处于动画中间态）。

### 4.F 历史对比 — **P1**

#### FR-F1｜本地快照自动保存 — **P1**

- **输入**：每次完成（或中断）的运行。
- **输出**：本地历史记录一条。
- **验收标准**
  1. 自动保存，无需用户操作；保存对用户无感知阻塞（≤ 200ms）。
  2. 至少保留 50 条；超限按时间淘汰最旧。
  3. 快照内容与导出 JSON 同构（便于未来迁移）。
  4. 提供"清空历史"入口，二次确认后彻底删除。
  5. 不上传任何数据到网络（隐私约束，见 NFR-9）。
6. **（v1.2 新增，`04-security.md` 提出）三条存储约束**：
   - **Windows 必须用 `%LOCALAPPDATA%\ProxyLens\`，禁止 `%APPDATA%`** —— 后者是 roaming 目录，会被域漫游 / OneDrive 同步到服务器，等于把代理 host 与历史分数带出本机。这条优先级高于"是否加密"。
   - 文件权限 `0600` / 目录 `0700`，**创建时即带权限**（不得先 0644 再 chmod）。
   - history **每行只存聚合值，不存原始采样**（可把 NFR-10 从 20 MiB 压到 1 MiB 量级）。
   - "清空历史"必须**删除文件本身**，不是写入空数组（否则旧数据仍在磁盘块中）。
7. **不加密历史（v1.2 终裁）**：无口令加密 = 安全剧场（密钥必须与数据同盘）；有口令加密 = 每次启动一个口令框，且与 FR-G8"文件损坏必须回落默认值并启动成功"直接冲突。正确层次是磁盘加密（FileVault / BitLocker），README 给一句建议。替代方案是**字段最小化**（去掉密码、完整 URL、query、IP、机器标识）+ 可删除 + 不漫游。

#### FR-F2｜历史列表与对比视图 — **P1**

- **输入**：历史记录中选择两条。
- **输出**：并排数值 + Δ 差值 + 状态变化标记。
- **验收标准**
  1. 列表至少显示：时间、模式、总分、三分项分。
  2. 对比项至少包含：Δ总分、Δ三分项、各探测项状态变化（含"改善 / 恶化 / 不变"）。
  3. 状态降级必须高亮（US-09 第 4 条）。
  4. 若两条记录模式不同（如一条 `DIRECT` 一条 `SYSTEM`），必须显式警示"配置不同，差值仅供参考"。
  5. 对比结果可导出（复用 FR-E3/E4 结构，增加 comparison 段）。

### 4.H 应用基础能力

#### FR-H1｜启动与单实例 — **P0**

- **输入**：用户双击启动。
- **输出**：主窗口就绪，可立即操作。
- **验收标准**
  1. 冷启动到**可交互** ≤ 2s（macOS Apple Silicon 参考机）/ ≤ 3s（Windows x64）。
  2. 重复启动不产生第二个实例（或第二实例聚焦已有窗口），不得出现两个窗口各自跑检测。
  3. 启动过程中显示可感知的加载反馈（> 500ms 时必须出现）。

#### FR-H2｜版本与关于 — **P1**

- **输入**：无。
- **输出**：应用版本、构建时间、运行平台与架构、所依据的探测端点清单。
- **验收标准**
  1. 一处可见（≤ 2 次点击）。
  2. 端点清单必须与本次实际使用的端点一致（便于 R3 复现）。
  3. 版本号符合语义化版本，可被报告中的 `appVersion` 引用并一致。

#### FR-H3｜最小诊断日志 — **P2（可砍）**

- **输入**：运行过程中的错误事件。
- **输出**：本地日志文件，可在"关于 / 诊断"处导出。
- **验收标准**
  1. 默认仅记录错误与关键状态迁移，不记录完整响应体，不记录凭据（FR-A6）。
  2. 日志文件大小上限 5MB，超限滚动。
  3. **取舍说明**：brief 未明确要求此功能。纳入 P2 的理由是异常场景（第 6 章）中多个"用户看到什么"的追问需要落证据，且 R3 场景需要可转发的技术细节；若 M1/M2 人力紧张可**直接砍掉**，不影响任何 P0 验收。

| NFR-12 | 磁盘 | 磁盘 I/O | 检测过程**不写**临时大文件（下载内容即取即弃） | 监控磁盘写入量，应 < 1 MiB/次 | P1 |

### 5.1 NFR 的三条解读补充

1. **NFR-4 与 NFR-5 的"上限"是硬承诺，不是平均值。** 到期必须收口并给出已完成项的结果（哪怕不完整），不允许"超时了但还在跑"。这直接决定用户是否敢用（US-04）。
2. **NFR-7 与 NFR-9 是本产品的信任基础。** 用户测的是自己的敏感网络环境；任何"顺手上报"都会摧毁信任。UI 上要能一句话说清："本工具不联网上传任何数据"。
3. **NFR-8 直接影响 NFR-1。** 若必须依赖用户预装运行时，冷启动时间与首启成功率都会失控。因此**分发形态必须自包含**（具体形态由 `03-architecture.md` 定，本文只约束结果：干净系统可直接运行）。

## 6. 异常与边界场景矩阵

> 原则：**任何异常都必须翻译成"用户能据此行动的一句话"**；只报技术错误码 = 未完成。

| 16 | **导出目录无写权限** | 导出到只读目录 | 导出失败，保留结果不被清空 | "无法写入所选目录（无权限）。请换一个目录，或使用默认位置。" | 不影响结果与分数 |

### 6.1 三条全局异常原则

1. **归因必须指向"谁的问题"**：用户 / 代理 / 目标服务 / 系统环境 / 网络运营商。同一个 `NET_FAIL` 在 #1、#4、#5、#9、#10 中的文案必须完全不同。
2. **不确定就说不确定**：PAC（#17）、轻量档跳过、中断运行（#12）、流量耗尽（#18）都必须标注置信度，不许给出"看起来很确定"的分数。
3. **不提供任何证书校验降级入口**（#5，v1.2 终裁）。无设置项、无 CLI 开关、无环境变量，且不得作为建议出现在任何结论文案中。宁可测不出，也不降低安全标准——因为"测不出"是诚实的，"在 MITM 下测出的分数"是有害的（`04-security.md` v1.1 同结论）。

## 7. 结论与建议的文案规则

> 这是本产品**最容易被做成黑箱**的地方。规则必须完全确定：给定指标 → 唯一结论 → 固定句式。`06` 提供阈值，`08` 提供呈现，但**判定逻辑与文案模板以本文为准**。

### 7.1 判定所需输入（谓词定义）

| 谓词 | 含义 | 判定依据 |
|---|---|---|
| `NET_OK` | 网络层通 | P6 至少一个端点 `PASS`，且成功率 ≥ 60% |
| `NET_PARTIAL` | 网络层部分通 | P6 两端点结果分歧，或成功率 30–60% |
| `NET_DEAD` | 网络层不通 | P6 全部 `NET_FAIL` / `TIMEOUT` |
| `AI_OK` | AI 可用性良好 | P3、P4、P5 全部 ∈ {`PASS`,`PASS_WITH_NOTE`} |
| `AI_BLOCKED` | AI 被策略/验证拦截 | P3 或 P4 ∈ {`BLOCKED_BY_POLICY`,`CHALLENGED`}，且 **`NET_OK` 成立** |
| `AI_LIMITED` | AI 部分可用 | AI 组中 1–2 项 `PASS`，其余为 `RATE_LIMITED` / `SLOW` / `NET_FAIL` |
| `AI_DEAD` | AI 全不可达 | P3、P4、P5 全部 `NET_FAIL` / `TIMEOUT` |
| `SPD_GOOD` | 速度达标 | 速度分项 ≥ 70（B 档及以上） |
| `SPD_POOR` | 速度差 | 速度分项 ∈ [30, 69]（C/D 档） |
| `SPD_BAD` | 速度不可用 | 速度分项 < 30，或 P1 判 `SLOW` 且吞吐 < 2 Mbps |
| `STB_GOOD` | 稳定 | 稳定性分项 ≥ 70 且连续失败次数 ≤ 1 |
| `STB_BAD` | 不稳 | 稳定性分项 < 55 或连续失败次数 ≥ 3 |
| `ENV_BAD` | 环境异常 | 命中第 6 章 #1、#9、#10 |

### 7.2 结论类型（7 类，互斥，按顺序优先匹配）

**匹配必须自上而下，命中即停**（避免一句话里塞两个结论）。

| 顺序 | 类型 | 判定条件 | 结论文案模板 | 建议（≤3 条，按需截断） |
|---|---|---|---|---|
| 1 | **C1 环境异常** | `ENV_BAD` | "当前环境无法完成有效检测：{原因}。本次结果仅供参考。" | ① 按提示修复环境（校准时间 / 连接网络 / 换 IPv4 网络）② 修复后重新检测 |
| 2 | **C2 完全不通** | `NET_DEAD` 且模式 = `SYSTEM`/`CUSTOM` | "当前{模式名}下无法访问境外网络，全部探测项均失败。" | ① 确认代理软件已启动并处于全局/TUN 模式 ② 切换到「自定义代理」填入实际地址重试 ③ 用「直连」跑一次，确认是否为代理自身问题 |
| 3 | **C3 能连，但用不了 AI**（**核心输出**） | `NET_OK` ∧ `AI_BLOCKED` | "网络本身是通的（{rtt}ms），但 AI 服务被拦截：{命中项列表}。这属于**能连不能用**。" | ① 换一个出口地区（当前被判定为{拦截类型}）② 若为人机验证，稍等 1–5 分钟再试 ③ 不要反复重连节点——本次问题不在速率 |
| 4 | **C4 AI 部分可用** | `AI_LIMITED` | "AI 服务部分可用：{可用项} 正常，{异常项} {异常原因}。" | ① 优先使用可用项 ② 对异常项按原因处理（限流→等待；超时→换线路）③ 若为 API 用途，建议存在风险，见「不稳定」提示 |
| 5 | **C5 能用但很慢** | `AI_OK` ∧ `SPD_BAD`/`SPD_POOR` | "AI 服务全部可达，但速度偏慢：下载 {mbps} Mbps（p50 {p50}），起播 {sec}s。日常可用，但看视频/传文件会等。" | ① 若主要用于聊天文本，当前速度够用 ② 若要视频/大文件，建议换线路 ③ 可跑「深度检测」确认是否持续慢 |
| 6 | **C6 能用但不够稳** | `AI_OK` ∧ `STB_BAD` | "AI 服务可达，但稳定性有隐患：{N} 次采样中失败 {M} 次，最长连续失败 {K} 次。" | ① 长任务（如 API 批处理、大文件）可能中断 ② 建议在稳定时段使用，或换线路 ③ 稍后复测确认是否为临时波动 |
| 7 | **C7 状态良好** | 以上均不命中（即 `AI_OK` ∧ `SPD_GOOD` ∧ `STB_GOOD`） | "综合表现良好：AI 服务全部可用，下载 {mbps} Mbps，{N} 次采样全部成功。当前{模式名}可以顺畅使用 AI。" | ① 无需操作 ② 如需留存，可导出报告 |

### 7.5 建议生成优先级

当命中条件允许给出多于 3 条建议时，按此顺序截断（保证留下最可执行的）：

1. 修复环境类（时间 / 网络）— 不修则一切无意义
2. 归因澄清类（"这不是速率问题"/"这与代理无关"）
3. 立即可尝试的对照实验（切直连重跑）
4. 配置调整（换出口地区 / 换 `socks5h://`）

## 8. 平台差异矩阵（Windows vs macOS）

> 目标：**同一套产品语义，两个平台的用户看到一致的结论**；差异只体现在"怎么拿到信息"和"系统怎么拦你"，不体现在功能缺失上。
> 若某平台做不到，必须降级为**显式标注的不确定**，不得静默撒谎。

| 维度 | macOS（12+，Intel / Apple Silicon） | Windows（10 / 11，x64 / arm64） | 产品要求 |
|---|---|---|---|
| **系统代理探测** | 读取系统网络设置中的 HTTP / HTTPS / SOCKS 配置与自动配置脚本（PAC）；TUN 接管时通常表现为"系统代理未开"，需靠路由/网卡特征识别 | 读取 WinINET 级系统代理（含 PAC）与注册表级设置；TUN 接管同样需靠网卡/路由特征识别 | 两平台都必须能区分 `系统代理（HTTP/SOCKS）` / `TUN 或全局接管` / `直连` / `无法识别`（FR-A4）。**TUN 识别是两平台共同难点，允许 `无法识别`，但必须显式展示而非猜** |
| **环境变量代理** | 常见（本机实测存在 `HTTP_PROXY/HTTPS_PROXY`，brief §4） | 较少见但在 CI/开发机存在 | 两平台都需读取并纳入冲突检测（第 6 章 #14）。优先级：TUN > 系统代理 > 环境变量（须在报告里写明所采用的优先级顺序） |
| **权限要求** | **不需要**管理员权限 / 不需要提权（不修改系统设置、不装驱动） | **不需要**管理员权限（同上） | **硬要求**：安装与运行**均不得**触发 UAC / 提权弹窗。若技术上不得不提权，须回传 PM 重新评审（会严重伤害首次体验与信任） |
| **首次运行拦截** | **Gatekeeper**：未签名/未公证的应用会被阻止（"无法打开，因为无法验证开发者"） | **SmartScreen**："Windows 已保护你的电脑"蓝色提示 | ① 必须在 `03`/`10` 阶段决定签名与公证策略；② **M1 允许未签名**，但必须在 README 提供两平台各自的**一次点击绕过图文说明**（macOS：右键打开 / 系统设置里允许；Windows：更多信息→仍要运行）；③ M3 分发前**必须**完成签名/公证，否则视为未达 Exit Criteria |
| **分发形态** | 优先单文件可执行；`.app` 包或 `.dmg` 可后续 | 优先单文件 `.exe`；安装包可后续 | 两平台形态可不同，但都必须满足 NFR-8（零预装运行时）与 NFR-1（冷启动） |
| **配置与数据目录** | 用户目录下的应用支持目录（遵循平台惯例） | 用户目录下的应用数据目录（遵循平台惯例），**不写**系统目录 | 不得写入需要管理员权限的位置；卸载/清空后不留残余（NFR-10）；路径在"关于/诊断"中可见（便于 R3 定位） |
| **字体与中文渲染** | 系统中文字体（苹方）渲染正常，字重层次丰富 | 微软雅黑 / 思源黑体，需注意**字重缺失**导致层次塌陷 | ① 字体选型与字重回退链由 `08` 定；② 硬要求：**中文不得出现缺字方块、不得因字体缺失导致布局错位**；③ 报告中中文字符在两平台纯文本查看器均正常（UTF-8） |
| **高 DPI / 缩放** | Retina 2x，需保证非整数缩放（如 1.5x）下不糊 | 常见 125% / 150% 缩放，且多显示器混合 DPI | ① 界面在 100%–200% 缩放下均不糊、不裁切；② 多显示器不同 DPI 拖动窗口时不得出现尺寸跳变；③ 截图友好摘要（FR-E5）在 125% 下仍可一屏完整 |
| **窗口与单实例** | 关闭窗口后是否退出进程需明确（建议退出，避免幽灵进程） | 同上；并需处理任务栏图标残留 | 两平台行为一致（FR-H1 第 2 条）；退出后**不得**残留后台进程（NFR-2 的隐含要求） |
| **网络环境变化** | 切 Wi-Fi / 插拔网线 / 睡眠唤醒后网络变化需被识别 | 同上，另需处理"有线/无线同时在线" | 检测开始前与运行中需感知网络变化；若运行中网络切换，必须中止本次并提示"网络环境已改变，请重新检测"（**不得**把两段不同网络的数据混算） |
| **IPv6 行为** | 系统默认可能优先 IPv6 | 同上 | 两平台都需正确处理 IPv6-only 与双栈回退（第 6 章 #9）；结论文案一致 |
| **代理认证** | 支持 `user:pass@` 基本认证 | 同上；**不**支持 NTLM / 域认证（企业环境） | 不支持的部分必须在 UI 明确说明，避免用户以为填错。NTLM 支持**首版不做**（用户群为 R1/R2，非企业域环境） |
| **时间偏差检测** | 需可读取系统时间并与网络时间对比 | 同上 | 第 6 章 #10 两平台行为一致 |

### 8.1 平台验收的"等价性"原则

> **测试判定标准**：同一网络环境、同一时间、分别用两平台客户端跑全量检测，以下三项必须一致，否则视为缺陷：
> 1. **各探测项的状态枚举一致**（允许 `NET_FAIL` 的具体子原因不同）；
> 2. **结论类型一致**（C1–C7 落在同一类）；
> 3. **分项分差 ≤ ±15**（网络本身有波动，允许一定差异，但不得出现"一个说能用另一个说不能用"）。
>
> 允许不一致：具体吞吐数值、出网方式的**识别细节**（TUN 识别能力可能不同）、耗时。

### 8.2 平台相关风险（提前标红）

| 风险 | 影响 | 缓解 |
|---|---|---|
| macOS 未签名导致 R1 首次打不开 | 首启失败率飙升，直接劝退 | M1 就提供绕过图文；M3 必须公证 |
| Windows arm64 生态（webview/原生依赖）可能缺失 | 该架构无法交付 | 若不可行，M1 明确只交付 x64，并在 README 与关于页写清支持矩阵，**不得**静默失败 |
| TUN 模式识别在 Windows 上不易做准 | 出网方式显示 `无法识别`，用户困惑 | 允许"无法识别"但必须给出可操作提示（"可在设置中手动选择直连或填代理地址"） |
| 多显示器混合 DPI | 界面错位、截图糊 | 列入 M2 Exit Criteria 的必测项 |

### M1｜可运行 MVP（"能跑通、结论可信"）
